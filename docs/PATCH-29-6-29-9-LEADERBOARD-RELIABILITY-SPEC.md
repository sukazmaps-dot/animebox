# AnimeBox: ТЗ на патчи 29.5–29.9 — рейтинг и Зал славы

Дата: 14 октября 2026 года, Asia/Qyzylorda. Границы рейтинговых периодов остаются UTC.
Статус: техническое задание; миграции и восстановление production по этому документу ещё не выполнены.

## 1. Цель и подтверждённая исходная ситуация

Сделать рейтинг проверяемым и устойчивым к очистке технических событий, сбоям планировщика, повторным запускам и сигналам антинакрутки. Визуальную доработку выпускать отдельно от изменений расчёта.

Проверка рабочей базы и публичного API 13 октября UTC / 14 октября по времени пользователя показала:

- SQL-расчёт за всё время возвращает 26 пользователей с положительным засчитанным временем. Расхождений с суммой progress.active_ms у этих пользователей нет.
- Публичный API возвращает 25 пользователей: lll с 2 160 411 мс, примерно 36 минутами, находится на 12-м месте в SQL, но исключается обработчиком API.
- Причина исключения — событие watch_trust_assessed со state=high_risk от 29 сентября, сигналами repeated_seek_forward и extreme_rejection_ratio. Это объясняет скрытие; само по себе не доказывает накрутку или ложное срабатывание.
- Текущая неделя имеет 2 участника, текущий месяц — 5 в существующем расчёте. Массовую потерю участников эти данные не подтверждают.
- В leaderboard_seasons отсутствуют завершённые недели 2026-09-28 и 2026-10-05. Последняя сохранённая неделя — 21–27 сентября; сентябрьский месячный архив существует.
- Последний зарегистрированный запуск отдельной задачи leaderboard-seasons — 28 сентября. Последний зарегистрированный запуск premium-lifecycle, которая также вызывает архивацию, — 4 октября. В cron.job нет задачи архивации рейтинга.
- Очистка запускает cleanup_animebox_watch_hot_data(14, 30): heartbeats удаляются через 14 дней, завершённые sessions — через 30.
- Неделя, месяц и закрытие сезона используют heartbeats. Постоянного агрегата по дням, достаточного для этих расчётов, в рассмотренной реализации нет.
- На момент проверки самый ранний оставшийся heartbeat — 29 сентября. Следовательно, полноту недели 28 сентября — 4 октября нельзя гарантировать только по оставшимся событиям.
- Существующая функция финализации не пересчитывает уже созданный сезон. Серверная обвязка обрабатывает только предыдущую неделю и предыдущий месяц, а не все пропуски.

Не считать все часы сентябрьского архива ошибочными: для большинства проверенных лидеров они согласуются с накопленной статистикой. Не выводить сентябрьское время вычитанием октября из all-time: это не надёжное восстановление распределения по датам.

## 2. Общие правила расчёта

1. Единица хранения — целые миллисекунды; округление допустимо только при отображении.
2. Учитывать серверное accepted_ms. Позиция плеера, длина просмотренного диапазона, ручная отметка эпизода и время открытой вкладки не заменяют засчитанное время.
3. Неделя начинается в понедельник 00:00 UTC, месяц — первого числа 00:00 UTC. Интервал полуоткрытый: starts_at <= received_at < ends_at.
4. Время относить к received_at события, как в текущем расчёте. Переход сессии через полночь не переносит весь просмотр на дату её создания.
5. Сохранить действующее ограничение времени одного эпизода в пределах периода. Сначала суммировать события/дни по user_id и episode_id за весь период, затем один раз применять лимит длительности эпизода. Применение лимита отдельно к каждому дню меняет правила и завышает итог при повторных просмотрах.
6. Сохранить текущую семантику завершений: считать completed_at в границах периода. Повторный просмотр не должен автоматически создавать второе завершение в рейтинге.
7. All-time продолжает использовать постоянный progress.active_ms. Не заменять его неполными восстановленными дневными агрегатами.
8. При равном времени сохранить детерминированный порядок: active_ms DESC, last_watched_at DESC, user_id. Явно определить NULLS LAST и применять одинаково в текущем и архивном рейтинге.
9. Правила антинакрутки, участия и наград должны иметь версии. Изменение правила нельзя незаметно применять к уже выданным наградам.

## 3. Патч 29.5 — композиция и размеры иконок

Проверить 320, 390, 768, 1180, 1440, 1920 px, светлую/тёмную тему, длинные имена, наборы owner+sponsor+premium, пустой рейтинг, 1/2/3/100 участников. Нет горизонтального переполнения, обрезания знаков и наложений; порядок DOM соответствует чтению страницы. Проверка производственной страницы обязательна в дополнение к CSS-фикстурам.

## 4. Патч 29.6 — сохранение данных рейтинга, P0

### 4.1 Срочный этап сохранности

До изменения расчётов измерить размер heartbeats/sessions, скорость роста, время очистки и доступный объём базы. Увеличить срок хранения согласованно для обоих источников: безопасный исходный ориентир 60 дней событий и не меньше 60 дней связанных сессий. Выбор срока подтвердить замерами, а не хранить события бессрочно.

Это временная защита оставшейся истории, а не восстановление уже удалённой. Существующее расписание очистки должно получать новые параметры; изменения только SQL default недостаточно, поскольку cron передаёт 14 и 30 явно.

### 4.2 Постоянный дневной агрегат

Предлагаемая таблица: animebox_watch.leaderboard_daily_activity. Окончательное имя выбрать по существующим соглашениям репозитория.

Поля:

| Поле | Назначение |
| --- | --- |
| user_id | Владелец засчитанного просмотра |
| episode_id | Эпизод для лимита времени |
| activity_date | Дата received_at в UTC |
| accepted_ms | Сумма засчитанных миллисекунд, bigint, >= 0 |
| last_watched_at | Последнее событие в дневном агрегате |
| updated_at | Время обновления агрегата |

Уникальный ключ: (user_id, episode_id, activity_date). Индекс по activity_date и user_id для периодных выборок; дополнительные индексы добавлять по EXPLAIN, а не предположительно.

### 4.3 Запись и заполнение

- Обновление должно быть в одной транзакции с записью принятого heartbeat. Если heartbeat не записан, агрегат не увеличивается.
- Повтор запроса с тем же идентификатором/последовательностью не увеличивает счётчик второй раз. Сначала проверить реальные ограничения таблицы и ветки обработки конфликтов.
- Разрешены trigger на фактическую вставку или изменение ingestion RPC; выбрать после анализа того, изменяется ли accepted_ms уже существующего события.
- Если accepted_ms может обновляться, обработка должна учитывать дельту. Вариант «всегда прибавить новое значение» запрещён.
- Нулевые и отклонённые события не увеличивают агрегат.
- Историческое заполнение выполняется из сохранённых heartbeats JOIN sessions. Для каждого дня фиксируется покрытие исходными данными.
- Заполнение при работающем ingestion должно иметь однозначную границу/блокировку или отдельное поколение агрегатов. Простой upsert(sum) поверх параллельных прибавлений может потерять новые события; sum + upsert(increment) может задвоить историю.
- После заполнения сверить сумму accepted_ms по пользователю, эпизоду и дню с исходными событиями в одном согласованном снимке.
- Сохранность дневного агрегата не должна зависеть от существования очищаемой sessions/heartbeat-строки. Каскадное удаление технической истории не удаляет дневные результаты.
- Правила удаления аккаунта и персональных данных сохранить; бессрочное хранение агрегатов не отменяет удаление пользователя.

### 4.4 Доступ и миграция

Новая миграция через Supabase CLI, отдельная от уже применённых файлов. Таблица не открывается anon/authenticated для прямой записи. RLS включён, grants минимальны, серверный RPC имеет фиксированный search_path и проверенный набор execute-разрешений.

Сначала таблица и запись, затем заполнение и сверка, затем переключение чтения. Очистка подробных событий возвращается к экономному сроку только после доказательства независимости расчётов от них.

### Приёмка

Повтор heartbeat не меняет результат; accepted_ms=0 даёт нулевую дельту; переход UTC-полуночи создаёт два дня; удаление старых heartbeats и sessions не меняет периодный итог; параллельные запросы не теряют счётчики; RLS не допускает запись клиентом.

## 5. Патч 29.7 — расчёты, участники и антинакрутка, P1

### 5.1 Единый расчёт периодов

- Общая SQL-функция расчёта произвольного закрытого UTC-интервала. Текущий рейтинг и финализация используют одну реализацию лимитов, сортировки и завершений.
- Источник времени для week/month — дневные агрегаты. Для неполного начального периода вернуть признак покрытия, а не незаметно смешивать его с all-time.
- Сначала формировать полный набор допустимых участников, сортировать и присваивать место, затем выбирать top-100. Не фильтровать участников уже после top-100, иначе места и количество строк расходятся с полным рейтингом.
- Личная позиция вне top-100 возвращается отдельно с настоящим местом; не становится 101-м местом из-за положения в массиве ответа.
- В ответе разделить entries, me, eligibleParticipantCount, periodBounds, computedAt, calculationVersion и coverage. Имена уточнить по типам проекта.
- Дефолт p_limit, размер страницы и количество зарегистрированных аккаунтов не трактуются как число участников. Пользователь с нулевым засчитанным временем не обязан попадать в рейтинг.

### 5.2 Политика доверия

Текущее исключение lll — следствие существующей политики, а не пропажи SQL-строки. Исправление нельзя свести к удалению всех high_risk-фильтров.

- Зафиксировать продуктовую политику: какие события исключают время, какие ограничивают только получение наград, когда и как снимается ограничение.
- Предпочтительный дизайн: подтверждённое время хранится, решение о награде отдельно; пользователь не исчезает молча, а видит понятный статус собственной позиции. Детальные сигналы и внутренние метрики не публиковать другим пользователям.
- Если принято исключать конкурентное время, применять решение к определённой сессии/эпизоду/интервалу. Не распространять одно событие на весь all-time без явного решения и версии политики.
- Решение хранить отдельно от короткоживущей аналитики product_events: scope, reason_code, status, decided_at, expires_at при временном ограничении, policy_version.
- Проверить случай lll по фактам конкретной сессии. Не объявлять событие ложным только потому, что пользователь отсутствует в рейтинге.
- Одинаковая политика для текущего рейтинга, личной позиции, Зала славы и наград.
- Убрать зависимость полноты trust-выборки от произвольного лимита 1000 событий: SQL EXISTS/агрегация по участникам или явная пагинация.

### Приёмка

Сценарии 0/1/2/3/26/100/101/150 участников; me на 1/12/100/120 месте; одинаковое время; ограниченный участник внутри top-100; события доверия больше 1000. Реальные места не пересчитываются по индексам урезанного массива. All-time до и после патча остаётся равным постоянному progress по каждому участнику при одинаковой политике участия.

## 6. Патч 29.8 — планировщик и восстановление архивов, P1

### 6.1 Независимый планировщик

- Создать Supabase pg_cron-задачу, вызывающую защищённый endpoint Railway либо специализированный DB job после проверки зависимостей наград. Не рассчитывать на исполнение vercel.json на Railway.
- Для HTTP-вызова секрет находится в Vault и в серверном окружении; в URL, Git и логах его нет. Использовать существующую схему авторизации или отдельный секрет с минимальной областью действия.
- Основной запуск ежедневно, например 00:20 UTC. Повторный запуск — 01:20 UTC при отсутствии успешной обработки; расписание согласовать с нагрузкой.
- Проверять успех приложения, а не только успех очереди pg_net. HTTP 401/500 и постановка запроса в очередь не являются успешной архивацией.
- Lease блокирует параллельные обработчики; функция финализации имеет защиту от конкурентного создания одного периода.

### 6.2 Догоняющая обработка

- Строить список завершённых недель и месяцев от явно заданного начала поддержки/восстановления до текущей UTC-границы.
- Вычитать уже успешно финализированные периоды. Не включать текущую неделю 12–18 октября и незавершённый октябрь.
- Обрабатывать самые старые пропуски первыми, с лимитом периодов и бюджетом времени. При исчерпании продолжать следующим запуском.
- Разделять состояния pending, running, complete, partial, failed или эквивалентный журнал. Само наличие строки leaderboard_seasons не доказывает успешную полноту архива.
- Ошибка одного периода не должна превращаться в общий успешный результат с пустым seasons: записать failed, причину и повторяемость.
- Проверять точные UTC-границы и period_key. Финализация будущего, произвольного или уже открытого периода запрещена серверной валидацией.

### 6.3 План восстановления текущих пропусков

1. Сохранить оставшиеся события и собрать отчёт покрытия по дням.
2. Для 5–11 октября сверить полный набор сохранившихся событий и расчёт с дневными агрегатами. Создать архив после успешной сверки.
3. Для 28 сентября — 4 октября найти пригодный датированный источник для удалённой части: разрешённый backup/PITR либо другой проверенный постоянный журнал. Не считать отсутствие heartbeat доказательством нулевого просмотра.
4. Восстановление backup выполнять в изолированную среду для извлечения нужных данных; не откатывать рабочую базу целиком.
5. При отсутствии источника сохранить статус неполного покрытия. Не выдавать частичный топ за окончательный сезон и не начислять награды по недоказанным местам.
6. Сентябрьский архив не переписывать автоматически. Сначала сухой расчёт различий по участникам, местам, времени и наградам; замена только при доказанной полноте источника.

### 6.4 Идемпотентность наград

- Повторный запуск не создаёт вторую награду, рамку или продление срока.
- Использовать существующие уникальные ключи сезона/участника/типа награды; проверить реальные ограничения до реализации.
- Уже полученные награды не отзываются молча из-за новой формулы.
- Для поздно восстановленных сезонов явно определить начало и конец действия рамок. Не выбирать автоматически между исторической датой и датой восстановления.
- Корректировка архива отделена от выдачи наград, имеет dry-run и аудит изменений.

### Приёмка

Повтор и параллельный запуск оставляют один архив и один набор наград; пропуск двух недель догоняется; будущий период отклонён; частичное покрытие не получает complete; ошибка авторизации заметна в мониторинге; финализация укладывается в бюджет endpoint.

## 7. Патч 29.9 — прозрачность интерфейса и контроль, P2

- Рядом с текущим рейтингом показывать реальные даты периода и пояснение «Границы периода — UTC».
- Указать число участников с засчитанным временем. «Топ-100» означает максимальный размер списка, а не обещание 100 строк.
- Различать отсутствие участников, ошибку загрузки, ожидание архивации и неполное историческое покрытие.
- Пустой завершённый сезон не исчезает бесследно: API/UI различают «нет засчитанных просмотров» и «архив не рассчитан».
- Зал славы показывает только завершённые периоды; partial не оформляется как окончательный пьедестал.
- Формат времени одинаковый в профиле/рейтинге/архиве для одной и той же метрики. Подпись объясняет различие общего и конкурентного времени, если политика создаёт такое различие.
- В админке: последний успешный запуск, ожидаемый последний завершённый период, список пропусков, покрытие данных, версия расчёта, список ограничений, безопасный dry-run восстановления.
- Метрики: продолжительность задания, обработанные/пропущенные/ошибочные периоды, возраст последней успешной обработки, число неполных периодов, расхождения all-time с progress.
- Сигнал деградации: завершённый период отсутствует после допустимого окна обработки; повторные ошибки cron; очистка опережает агрегацию. Канал уведомлений подключать отдельно в рамках разрешённой интеграции.

## 10. Патч 29.10 — масштаб рамок в чате и социальных блоках, P1

Дополнение по новым скриншотам: рамка пользователя ghoul cat в сообщении визуально не согласована с размером аватара. Скриншот подтверждает симптом, но точную причину нужно проверить на фактически используемом компоненте и SVG.

### Диагностика

- Найти активную реализацию чата и её ветку выбора обычной, сезонной, milestone и owner/sponsor-рамки. Не исправлять только комментарии: у GlobalChatV11Client есть собственные avatarWrap/avatar/frame-стили.
- Снять computed width/height/inset/transform для оболочки, аватара и декоративного слоя. Проверить правила общего вида img, мобильные overrides и вложенные изображения знаков.
- Проверить viewBox и фактическое внутреннее отверстие каждого SVG: одинаковые внешние размеры файлов не гарантируют одинаковый диаметр видимого ободка.
- В рассмотренном базовом CSS чата оболочка и frame имеют 42×42 px, а avatar — 36×36 px с inset 3px. Это исходная геометрия для проверки, а не доказанная причина дефекта конкретного кадра.

### Решение

- Единая оболочка аватара с --avatar-size и отдельным декоративным слоем. Рамка центрирована относительно центра изображения, не относительно строки сообщения.
- Размер выбирать по контексту: исходный ориентир изображения в плотном чате 36 px desktop / 32–36 px mobile. Максимальный внешний габарит декора резервируется сеткой сообщения; он не должен нависать на ник и соседнюю строку.
- Масштаб рамки калибровать по геометрии её SVG через метаданные профиля рамки: размер отверстия/scale/offset. Не применять один случайный отрицательный inset ко всем ассетам.
- Avatar и frame имеют aspect-ratio: 1, flex-shrink: 0. Изображение аватара object-fit: cover, декоративный ассет object-fit: contain, pointer-events: none.
- Overflow оболочки допускает декор; родитель сообщения оставляет достаточный отступ, чтобы внешний край не обрезался viewport чата.
- Наличие рамки не меняет базовую линию ника, высоту заголовка и начало текста. Отсутствующий/просроченный/невалидный ключ даёт обычный аватар без сломанного изображения.
- Для плотного списка использовать существующие статические ассеты, сохранить reduced-motion. Не подгружать анимированные тяжёлые рамки для каждого сообщения.
- Устранить дублирование геометрии чата, комментариев и списка участников там, где это не меняет размеры большого профиля и мини-профиля.

### Приёмка

Проверить все доступные типы рамок, разные обрезки лица, сообщения с цитатой и без, соседние сообщения одного пользователя, ответы, системные сообщения, длинный ник, owner+sponsor, отсутствие аватара. Ширины 320/390/768/1440/1920, zoom 100/125/150%, обе темы. Центры рамки и аватара совпадают с допуском 1 CSS px; декоративный слой не перекрывает текст и не обрезается. Проверить production DOM, а не только изолированную фикстуру.

## 11. Патч 29.11 — доступность жанровых подборок, P1

На скриншоте /anime/genre/psychological вместо карточек показано «Подборка временно недоступна». Другой скриншот показывает переход к этому жанру со страницы «Обещанный Неверленд». По нему отдельный новый баг hero-верстки не установлен.

### Подтверждённая логика

- Страница разрешает slug psychological в значение Psychological и вызывает getAnimesWithShikimori с genres=[genre.value], page=1, limit=24.
- Ошибка запроса перехватывается, items остаётся пустым. SeoAnimeLanding показывает одинаковый fallback и для ошибки, и для пустого результата.
- У маршрута revalidate=3600. Проверить, не сохраняет ли генерация пустой ответ после временного сбоя на срок кеша; без live-проверки это гипотеза.

### Требования

- Проверить преобразование Psychological к фильтрам каждого источника, реальные параметры запроса, timeout, rate-limit и нормализацию жанров. Причину установить до изменения UI.
- Ввести различимые исходы success / empty / unavailable. В логах — slug, нормализованный фильтр, источник, причина, длительность; без секретов.
- Подборка содержит только тайтлы запрошенного жанра. При ошибке нельзя подставлять общую популярную ленту под заголовком «Психологическое».
- При сбое внешнего источника отдавать последнюю успешную жанровую подборку либо проверенную локальную выборку того же жанра. Отметить актуальность при необходимости.
- Успешные данные и временные ошибки имеют разные правила кеширования. Краткий сбой не должен заменять полезный кеш пустой страницей на час.
- В fallback разместить действующую ссылку на каталог с уже выбранным жанром. Формат параметра взять из действующего search API, не выдумывать.
- Если кэш/источник недоступны, показать компактное сообщение и повторную попытку без большой декоративной пустоты. Существующая общая ссылка в каталог может остаться второстепенной.
- Сохранить canonical, breadcrumbs, стабильные ссылки и структурированные данные. ItemList содержит только фактически отображаемые тайтлы; не объявлять несуществующие карточки.
- Инвалидация после восстановления источника обновляет жанровую страницу. Действующее публичное индексирование не отключать глобально ради временного сбоя.

### Приёмка

Psychological, Drama, Action и жанр с небольшим количеством тайтлов; прямой вход и переход из hero; валидный/невалидный slug; timeout/429/500; доступный успешный кеш при недоступном источнике; восстановление источника; повторная загрузка. Карточки соответствуют жанру, ссылки открываются, фильтр fallback сохраняется, страница не остаётся пустой после восстановления. Проверки включают данные/API и страницу, а не только скриншот.

Дополнительный порядок: после сохранения рейтинговой истории рамки 29.10 и жанровые страницы 29.11 можно выпускать независимо от архивного восстановления. У каждого отдельный PR и собственная приёмка.
