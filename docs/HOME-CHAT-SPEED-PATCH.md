# AnimeBox — быстрое открытие главной и чата

## Назначение
Ускорить появление полезного содержимого на телефонах и ПК, уменьшить зависимость первого экрана от внешних API, сохранить функциональность чата, персональные рекомендации и стабильность карточек. Реализовать изменения на текущем Node/Next.js, без новых платных сервисов и миграций.

## Что уже есть и сохраняется
Главная получает initialPopular/initialOngoing с сервера. Герой поддерживает SSR, размеры изображений и приоритет первого изображения. Карточки используют responsive sizes. Персональные рекомендации загружаются отдельным динамическим компонентом, имеют общий кэш страниц и append-only догрузку. Чат загружает ограниченную первую историю, авторов и реакции пакетами. Эти механизмы сохраняются; повторно внедрять их под другим названием не требуется.

## Диагноз
1. Холодная главная ждёт getAnimesWithShikimori для двух групп. Даже при наличии сохранённых проверенных тайтлов первый экран зависит от внешней сети.
2. Чат async page ждёт полной истории с оформлением авторов перед отдачей своей части страницы. Пользователь не видит содержимое маршрута во время ожидания.
3. Realtime INSERT ожидает ensureAuthors перед добавлением текста сообщения. Медленная загрузка профиля задерживает уже полученное сообщение.
4. Параллельные события одного нового автора могут повторять author lookup.
5. После неудачного server bootstrap страница получает пустой initialPage и не пытается самостоятельно восстановить последние сообщения.

## Реализация: главная
- При заполнении общего кэша сначала запросить сохранённый playable каталог, независимо для популярных и продолжающихся тайтлов.
- Получать максимум 12 карточек в каждой группе; запросы групп выполняются параллельно.
- Если группа сохранённых карточек непустая, вернуть её без обращения к внешнему metadata API.
- Если сохранённая группа пуста или источник недоступен, использовать существующий getAnimesWithShikimori только для этой группы.
- Не смешивать карточки разных групп и не удалять жанры, даты и поля, необходимые для ранжирования.
- Сохранённые карточки уже проверены playable-view: не делать повторную availability проверку.
- Для внешней ветки сохранить существующую проверку registry и ограниченные фоновые пробы.
- Кэш проверенного результата — 300 секунд, новое поколение home v7.
- Сохранить текущие SSR initial props, hero geometry, клиентскую персонализацию, историю и рекомендации.

Ограничение: сохранённый первый экран отражает содержимое локального каталога. Он не гарантирует свежесть текущего AniList рейтинга. Пустая локальная база всё ещё требует внешнего API; изображение по-прежнему зависит от media/origin cache. Не заявлять, что устранена любая задержка.

## Реализация: маршрут чата
- Выделить async загрузку истории в отдельную server component ChatHistory.
- Обернуть её в Suspense с лёгкой оболочкой ChatLoadingShell.
- Добавить app/chat/loading.tsx для переходов App Router.
- Оболочка использует ту же сетку, заголовок и viewport CSS, что и готовый чат, уменьшая скачки.
- Показать понятный статус загрузки и aria-busy; декоративные skeleton блоки скрыть от скринридера.
- Первую историю оставить ограниченной 24 сообщениями. Не превращать историю в публичный долгоживущий кэш: удаления и модерация должны оставаться актуальными.
- Сохранить noindex и force-dynamic.

Это streaming первого ответа: оболочка появляется до истории. Сам по себе Suspense не ускоряет SQL и не означает мгновенной загрузки сообщений. Уже имеющиеся запросы авторов и реакций остаются пакетными.

## Реализация: realtime и авторы
- При INSERT проверить payload, создать сообщение и сразу добавить его в текущий список.
- Если автор уже известен, применить его сразу. Если неизвестен, показать существующее резервное представление и запустить загрузку автора отдельно.
- После получения автора обновить сообщения, у которых author отсутствует.
- Сохранить сортировку, дедупликацию IDs, реакции, scroll-to-bottom только если пользователь находился рядом с низом, индикатор новых сообщений и mark-seen.
- Вести Set авторов, уже ожидающих ответа. Не запускать параллельный lookup того же ID.
- Очищать pending IDs в finally, включая ошибки. Следующий запрос может повторить неудачный lookup.
- Не изменять авторизацию, ограничения отправки, slow mode, optimistic send, delete/report/moderation.

## Реализация: восстановление после ошибки
- Если SSR передал непустую историю, не делать повторный browser history fetch при монтировании.
- Если initialPage пустая, запросить актуальные последние сообщения через существующий /api/chat/messages, cache:no-store.
- Отменять запрос при размонтировании и не применять отменённый ответ.
- При восстановлении заполнить authorCache и nextCursor.
- Объединять историю с сообщениями, пришедшими через realtime во время ожидания; более новое локальное состояние имеет приоритет.
- На повторной ошибке показать существующее сообщение ошибки, не запускать бесконечный retry loop.

## Политика изображений и тяжёлых компонентов
В этой поставке не увеличивать число preload/priority изображений: конкуренция постеров с hero может ухудшить LCP на телефонах. Не загружать все ряды одновременно. Существующие responsive sizes, lazy images и динамические рекомендации сохраняются. Разделение дополнительных частей ProfilePreview и виртуализация длинной истории требуют отдельного измерения bundle/DOM, чтобы не сломать рамки, порталы и scroll anchoring.

## Приёмка
- С сохранённым каталогом загрузка первого экрана не вызывает внешний anime provider.
- При недоступном/пустом saved каталоге fallback продолжает работать.
- Тёплый кэш главной не повторяет registry read и фоновые пробы.
- Повреждённый registry не отравляет кэш пустым успешным результатом.
- Реальный маршрут чата отдаёт loading shell до завершения намеренно задержанной истории, затем сообщения в том же stream.
- У здоровой начальной истории нет повторной browser загрузки.
- Неизвестный автор не блокирует добавление сообщения.
- Повторные события одного автора не вызывают одновременные запросы его оформления.
- После unmount late response не применяется.
- SSR metadata, фильтры, cursor и порядок рекомендаций сохранены.
- TypeScript, ESLint изменённых файлов, предыдущие performance guards и полная Next production сборка проходят.

## Проверка после деплоя
Проверить главную и чат в новом и прогретом браузере: мобильный viewport и ПК, обычная сеть и throttling. Отдельно записать TTFB, LCP, INP, CLS, время первого сообщения, число network requests и bundle transfer. Сравнивать одинаковые страницы, устройства и условия; минимум несколько повторов, отдельно cold/warm.

Проверить вход гостем и пользователем, начальную историю, отправку/ответ/реакцию, загрузку старых сообщений, удаление и повторный вход. Проверить главную без истории и с историей, переключение настроения и append-only догрузку.

Не утверждать процент ускорения и баллы PageSpeed без замеров production. Серверные тесты подтверждают устранение блокирующих зависимостей; не моделируют мобильный радиоканал, декодирование изображений и нативную прокрутку.

## Публикация и откат
Отправить только файлы этой поставки в main после успешных проверок; secrets, generated bundles и незавершённые Cloudflare изменения исключить. Railway при включённом автодеплое собирает main. До успешного деплоя считать production неизменённым.

Для отката вернуть эти файлы и предыдущую cache generation, пересобрать. Миграций, новых env и изменений DNS нет.
