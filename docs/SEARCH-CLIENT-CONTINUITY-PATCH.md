# ТЗ: устойчивый поиск и последовательная догрузка каталога

Дата: 6 октября 2026. База: main c7ab458b.

## 1. Цель и пользовательский результат

Поиск должен сохранять пригодные карточки при частичном отказе, корректно переключаться между запросами и последовательно загружать страницы. Запросы быстрого локального поиска и полного поиска остаются параллельными. Пользователь может открыть карточку сразу после появления быстрого результата.

Это патч клиентской устойчивости. Он не обещает устранить всю задержку сети, восстановить отсутствующие источники видео или заполнить метаданные, которых нет у поставщика. Индексированный серверный поиск реализован предыдущим патчем.

## 2. Подтверждённые дефекты

1. В обработчике ошибки полного поиска выполняется дополнительное ожидание быстрого поиска. Проверка актуальности до этого ожидания недостаточна: за время ожидания пользователь может сменить запрос. Старый обработчик способен очистить метаданные и показать ошибку для нового запроса.
2. Быстрые результаты устанавливают hasNextPage=true без подтверждённой пагинации. Если полный поиск завершился ошибкой после появления быстрого результата, значение остаётся true. Observer начинает запрашивать следующую страницу по неподтверждённым результатам.
3. Страница увеличивается до запроса. При ошибке второй страницы автоматическая догрузка может снова увеличить её до третьей. Вторая страница пропускается.
4. Несколько сигналов observer или сочетание observer и кнопки до следующего React render способны несколько раз увеличить страницу. Одного состояния loading недостаточно для синхронной блокировки.
5. При ошибке догрузки очищаются метаданные первой страницы, хотя её карточки сохраняются.

Локальная рабочая копия также содержала ещё не опубликованную поддержку catalogMeta. В патч включается согласованная передача этой информации до интерфейса и короткий TTL для сохранённого резервного каталога.

## 3. Требования к владению запросом

Каждый запрос принадлежит поколению requestSequenceRef и своему AbortController. Запись результатов, ошибок, метаданных, пагинации и состояния loading разрешена только актуальному поколению, чей query совпадает с текущим liveQuery.

При вводе нового текста предыдущее поколение отменяется сразу; существующий debounce 90 мс сохраняется. При смене фильтров, настроения, режима каталога и навигации назад действуют существующие правила отмены.

После каждого дополнительного await в обработчике ошибки требуется повторная проверка актуальности. Отмена или ошибка старого запроса не должна разблокировать пагинацию нового запроса.

## 4. Быстрые результаты и полный поиск

- Быстрая ветка показывает непустые карточки только до завершения полной ветки и только для актуального запроса.
- Быстрые карточки не подтверждают наличие следующей страницы: hasNextPage=false до успешного полного ответа.
- Успешная полная ветка заменяет первую страницу, устанавливает фактическую пагинацию и снимает статус уточнения.
- При отказе полной ветки быстрые карточки остаются доступными; отображается сообщение о временной недоступности полного поиска.
- Если полный поиск упал раньше быстрого, обработчик может дождаться быстрой ветки. После ожидания он сначала проверяет поколение и лишь затем меняет интерфейс.
- Отказ обеих веток не стирает последние пригодные результаты.
- Пустой успешный полный ответ остаётся обычным результатом поиска; он не превращается в ошибку и не заменяется старым быстрым ответом.

## 5. Догрузка и повтор

Кнопка и IntersectionObserver используют одну синхронную блокировку. Первый допустимый сигнал захватывает её до setPageState. Повторные сигналы до React render ничего не делают.

Переход на следующую страницу запрещён при загрузке, ошибке, отсутствии подтверждённой следующей страницы или несовпадении query с liveQuery. Каждая новая загрузка блокирует продвижение; только актуальная успешная загрузка освобождает блокировку.

При ошибке страницы N:

1. Сохраняются карточки страниц 1..N-1 и метаданные первого ответа.
2. hasNextPage становится false, observer отключается.
3. Состояние page остаётся N.
4. «Повторить» увеличивает retryNonce и повторяет N, а не N+1.
5. Успешный повтор объединяет карточки через существующее устранение дубликатов по anime.id.
6. Фактический hasNextPage успешного ответа снова разрешает продвижение.

Автоматических повторов после ошибки нет. Это предотвращает цикл запросов при постоянно недоступном API.

## 6. Резервный каталог

AnimeListPayload получает необязательное catalogMeta с source='saved' и message. Клиент передаёт сообщение в существующую область статуса. Ответ резервного каталога удерживается в браузерном кэше 15 секунд; обычные успешные ответы сохраняют действующие TTL. Это позволяет быстрее увидеть восстановившийся основной источник.

Данная информация является сообщением о происхождении данных, а не подтверждением доступности каждого видеоисточника. Секреты и внутренние детали провайдеров в интерфейс не передаются.

## 8. Критерии приёмки

| Сценарий | Ожидаемое поведение |
|---|---|
| Два сигнала observer в одном такте | Ровно один переход страницы |
| Observer и кнопка в одном такте | Общая блокировка разрешает только первый переход |
| Новый ввод до debounce | Догрузка старого query запрещена |
| Полный поиск упал, preview ещё ожидается, пользователь сменил запрос | Старый preview и старая ошибка не изменяют новый поиск |
| Ожидаемый preview отвергнут после смены запроса | Старый обработчик также ничего не меняет |
| Preview виден, полный поиск упал | Карточки остаются, пагинация отключена |
| Страница 2 упала | Страница 3 автоматически не запрашивается |
| Повтор страницы 2 успешен | Карточки объединяются, продолжение снова возможно |
| Следующей страницы нет | Догрузка запрещена |
| Запрос отменён при размонтировании | Отложенные ответы не меняют состояние |
| Резервный каталог | Сообщение отображается, кэш ограничен 15 секундами |

Синтетические регрессии проверяют причинные последовательности без реальной сети. Они не заменяют измерение LCP/INP/CLS или проверку мобильного браузера. Публикация main сама по себе не подтверждает окончание Railway deployment.
