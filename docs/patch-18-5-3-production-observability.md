# Patch 18.5.3 — Production Observability & Incident Shield

## Goal

Turn the existing 17.5 System Health foundation into a production diagnostics layer that remains useful when AnimeBox grows from the first live users to thousands of requests.

The patch must answer four operational questions quickly:

1. Which critical API route is failing?
2. Is the failure a provider problem, an application exception, a rate-limit spike or a latency regression?
3. How large is the impact over the last hour and 24 hours?
4. Which request id can be correlated with an unhandled runtime incident?

## Architecture

### Bounded request telemetry

Critical API handlers are wrapped by `observeApiRoute`.

The wrapper:
- reuses `x-animebox-request-id` generated by the global edge shield;
- measures end-to-end route handler duration;
- always records 5xx, 429 and requests slower than 1500 ms;
- samples normal traffic at 1/8 and stores an estimated request weight of 8;
- never stores IPs, query strings, user ids, request bodies or response bodies;
- fails open if telemetry storage is unavailable.

Supabase stores only five-minute aggregate buckets in `system_request_metrics`, not one row per request.

### Latency histogram

Each bucket records weighted latency bands:

- <250 ms
- 250–500 ms
- 500–1000 ms
- 1000–2500 ms
- >=2500 ms

System Health derives approximate p95 and p99 values without retaining raw request timings.

### Incident shield

Handled provider/API failures remain normal response telemetry.

Only an exception that escapes a route handler opens/deduplicates a critical incident:
`request:<route>:unhandled`.

The incident metadata contains the AnimeBox request id, HTTP method, duration and a normalized error class, but no private request data.

### Retention

Metrics are retained for 30 days. The existing daily catalog availability cron performs bounded pruning through `prune_system_request_metrics`, avoiding another Vercel cron entry.

## Initial coverage

Patch 18.5.3 instruments the highest-value public runtime paths:

- `/api/anime`
- `/api/recommendations`
- `/api/discovery`
- `/api/players/kodik`
- `/api/anilibria`
- `/api/player/direct-source`

This gives visibility into catalog/search, discovery and the complete current playback-provider chain without adding telemetry writes to every low-value endpoint.

## System Health additions

The admin System Health snapshot gains:

- estimated API requests: 1h / 24h;
- server errors: 1h / 24h;
- 5xx rate: 1h / 24h;
- rate-limit hits: 1h / 24h;
- slow requests: 1h / 24h;
- approximate p95 / p99: 1h / 24h;
- max observed latency;
- live Supabase probe latency;
- live Cloudflare media-edge health, protocol and R2 binding state;
- per-route request/error/429/slow/p95/max table;
- request id metadata on runtime incidents.

Status escalation rules are traffic-gated so a single low-volume failure does not make the whole platform critical.

## Release gates

The patch is not ready until:

- the migration is present and service-role-only;
- telemetry remains sampled/bounded and privacy-safe;
- all six critical routes are wrapped;
- no raw URL or user identifier is stored;
- System Health exposes 1h/24h API runtime metrics;
- System Health probes Supabase and media-edge health fail-open;
- the existing daily cron prunes request telemetry;
- TypeScript, targeted lint, patch regression checks and production build pass.
