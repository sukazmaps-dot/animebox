# AnimeBox: подробное ТЗ на устранение дорогого SQL-поиска

## 1. Назначение и итоговое направление

Ускорить первый локальный поиск, который ещё не попал в процессный кеш, сохранив ранжирование, поддержку русского/английского названия, алиасов, опечаток и коротких запросов. Патч строится поверх main 396a31a232765daf4035b4ec79dcde992913b3be.

Первоначальная гипотеза о медленной проверке лимита не подтвердилась на Railway: она заняла 138 мс. Подтверждённый дорогой этап — lexical SQL. Защиту API и ограничения провайдеров не ослаблять. Источники не переписывать повторно: на Railway Frieren уже возвращает 28 эпизодов через availability и 33 озвучки через прямой Kodik API.

## 2. Исходные наблюдения

| Проверка на Railway до этого патча | Результат |
| --- | --- |
| instant naruto | HTTP 200, 17 карточек, полный ответ 7804 мс |
| rate-limit этап instant | 138 мс |
| lexical этап instant | 2975 мс |
| availability этап instant | 134 мс |
| Kodik Frieren серия 1 | HTTP 200, available, 33 озвучки |
| Кодик rate-limit / lookup / handler | 136 / 182 / 460 мс |
| Frieren episode-availability | HTTP 200, available, 28 эпизодов |

В базе anime_search_documents — 2094 документа. EXPLAIN ANALYZE вызова v2 naruto/40: Execution Time 2152,963 мс, 40 результатов. База уже содержит GIN search_text gin_trgm_ops и GIN title gin_trgm_ops. Проблема не в отсутствии любого индекса: старый запрос вычисляет дорогой score и лучший alias для всего корпуса до фильтрации.

Полное время HTTP включает сеть среды измерения, ответ и другие этапы. Оно не равно SQL execution time; не выводить скорость пользователя или CPU из одного curl.

## 3. Архитектура решения

Добавить отдельную серверную RPC search_anime_hybrid_lexical_v4(text, integer). Существующие v2 и обнаруженная в базе v3 остаются неизменными. v3 имеет другую форму результата и не используется текущей веткой приложения; её не удалять ради создания новой функции.

Новая функция выполняет:

1. Нормализацию query один раз в MATERIALIZED CTE.
2. Отбор кандидатов по индексируемым операторам search_text LIKE, similarity `%` и word similarity `<%`.
3. Нормализацию title и slug только для кандидатов.
4. Выбор лучшего alias; каждый alias нормализуется один раз в отдельном MATERIALIZED CTE.
5. Вычисление прежнего base_score и shape_closeness только для кандидатов.
6. Применение прежнего порога результата, сортировки и limit.

Не вводить произвольный ранний LIMIT на кандидатов: он может удалить правильный exact/alias match до ранжирования. Использовать существующий индекс, не создавать дополнительную таблицу, не переписывать весь каталог и не менять его синхронизацию.

## 4. Индексируемый отбор

Кандидат подходит, если нормализованный запрос не короче двух символов и:

- search_text содержит запрос;
- либо запрос не короче четырёх символов и проходит `%` или `<%`.

Пороги pg_trgm.similarity_threshold и pg_trgm.word_similarity_threshold — 0,22 только на время вызова функции. Не менять глобальные параметры базы или остальные RPC. Это широкий предварительный отбор, а не окончательный score: финальные пороги старого ранкера сохраняются.

GIN поддерживает указанные операторы. Фактический план проверяется EXPLAIN ANALYZE: ожидать Bitmap Index Scan существующего anime_search_documents_search_trgm_idx, а затем работу только с кандидатами. Короткие строки без извлекаемых триграмм могут требовать широкого просмотра; для них важна корректность, а не ложная гарантия индекса.

Перед CREATE FUNCTION в новом backend вызвать существующую extensions.similarity для регистрации параметров расширения. Это не устанавливает расширение и не меняет его версию.

## 5. Сохранение ранжирования

Не изменять численные коэффициенты старого v2.1:

- exact title и alias;
- prefix title и alias;
- contains title, alias и slug;
- similarity и word_similarity;
- shape_closeness с добавкой 0,07;
- ограничение итогового score единицей;
- пороги 0,55 для длины до 3, 0,38 для длины до 5 и 0,28 для более длинного запроса;
- tie-break: score, длина title относительно query, длина title, updated_at, anime_id.

Сохранить matched_text и match_kind exact/prefix/contains/fuzzy/weak. Не пытаться одновременно улучшить неоднозначное ранжирование франшиз: в этом патче оно служит контрактом для сравнения.

## 6. Права и безопасность

Новая функция SECURITY INVOKER. EXECUTE разрешён только service_role. PUBLIC, anon и authenticated не получают вызов RPC. Существующие права таблицы и RLS не изменяются. Секрет Supabase остаётся только на сервере.

Query передаётся обычным аргументом RPC, без динамического SQL. Сохранить лимит match_count 1–50. Нормализованный пустой/односимвольный запрос не возвращает каталог. Новая функция не обращается к профилям, сообщениям или другим персональным данным.

Проверить has_function_privilege для service_role/anon/authenticated и prosecdef. Запустить Supabase security advisors; отдельно отличать существующие замечания других функций от нового RPC. Не исправлять несвязанные ACL или политики без отдельного задания.

## 7. Подключение в приложении

lib/search-index-server.ts сначала вызывает v4 с query_text и match_count. Если сервер сообщает отсутствие функции/schema cache, вызвать прежнюю v2. При отсутствии v2 сохранить существующий fallback на legacy lexical.

При сетевой ошибке, permission denied или другой ошибке исполнения не запускать автоматическую цепочку дорогих fallback запросов: сохранить прежнюю обработку ошибки. Не увеличивать upstream retries.

Существующий ограниченный кеш lexical pool на 30 секунд остаётся. Размер пула, поддержка текстовых вариантов, окончательная обрезка до limit и публичный JSON-контракт API не меняются. Имя source local-index-v2 — существующий контракт клиента, оно не обозначает версию SQL RPC и сохраняется для совместимости.

## 8. Миграция и последовательность выпуска

Файл миграции создан CLI: supabase/migrations/20261006113022_indexed_lexical_search_v4.sql. В базе новая RPC создаётся до выкладки приложения. Поскольку приложение до этого использует v2, создание v4 не меняет текущий пользовательский поиск.

Миграция уже применена к существующему проекту. Затем функция была уточнена MATERIALIZED для scoring stages; итоговый файл содержит финальное определение. Все измерения финальной функции и проверки результатов относятся к этому определению.

В GitHub публикуются только миграция, переключение server loader, тест и это ТЗ. Не включать локальные Cloudflare configs, изменения зависимостей, незавершённые UI-файлы или переменные окружения.

## 9. Проверка качества на реальной базе

Сравнить первые восемь anime_id v2 и v4 для:

| Запрос | Назначение |
| --- | --- |
| naruto | английский exact/prefix |
| наруто | русский exact/alias |
| naruta | опечатка |
| фрирен | русский alias |
| friren | английская опечатка |
| ван писс | русский запрос с опечаткой |
| one piece | составное название |
| магичиская битва | длинная русская опечатка |
| na | короткий двухсимвольный запрос |

Фактическое сравнение: все девять последовательностей совпали. Это ограниченная матрица, а не доказательство эквивалентности для любого текста. Проверить также максимальный limit, пустой запрос и запрос без результатов.

Для дальнейшего регрессионного контроля tests/search-source-recovery.mjs проверяет реальный server module с fixture RPC: v4 используется первым, а при отсутствии миграции v2 продолжает работать. Сохраняются тесты общего кеша, разных preview/main limits, expiry, empty recovery и provider reasons.

## 10. Проверка производительности

До: v2 naruto/40 — SQL 2152,963 мс. Новая версия в отдельных измерениях дала 627,345 и 1065,318 мс. Развёрнутый план тела финальной функции дал 415,036 мс и отобрал 385 кандидатов из 2094 документов через GIN. Разница измерений показывает, что нельзя обещать фиксированное время ответа или процент для всех запросов.

Проверить на Railway после deployment:

1. Запросить новый уникальный query или дождаться TTL, чтобы не измерять только память процесса.
2. Записать timings.rateLimitMs, lexicalMs, availabilityMs, общий HTTP и число карточек.
3. Повторить тот же запрос до 30 секунд: проверить тёплый lexical кеш.
4. Повторить после TTL.
5. Проверить русский query, опечатку и короткий query.
6. Сравнить одинаковые условия и несколько повторов.

Не выполнять нагрузочный тест и не открывать параллельный поток сотен запросов на рабочую базу. Скорость первого видимого результата и постеров требует отдельного браузерного измерения. Время SQL не является LCP.

## 11. Критерии приёмки

- v4 доступна service_role и закрыта для браузерных ролей.
- Существующие v2/v3 не изменены и не удалены.
- Plan использует существующий GIN для исследованного naruto.
- Первые восемь результатов совпадают на девяти контрольных запросах.
- Сервисный RPC через Supabase client возвращает реальные результаты.
- При отсутствии v4 приложение сохраняет v2 fallback.
- При ошибке кеш не сохраняет пустой неудачный результат.
- TypeScript, ESLint, regression suite, prebuild guards и production build проходят.
- После деплоя проверяется Server-Timing; до этого не объявлять ускорение Railway подтверждённым.

## 12. Откат и оставшиеся задачи

Откатить переключение lib/search-index-server.ts на предыдущий main; таблицы и данные не затронуты. Не удалять v4 немедленно, пока возможны активные запросы новой версии. При необходимости удаления — отдельное согласованное действие после отката приложения.

За пределами патча: регион сервера/БД, доменные OAuth настройки, дополнительные провайдеры видео, рендер постеров и оптимизация контекстного smart discovery. Последний прежний endpoint availability уже успешно проверен на Frieren; это не подтверждает источники для каждого тайтла.

## 13. Итог проверки перед публикацией

Миграция применена. Сервисный Supabase RPC v4 вернул 40 строк и Naruto ID 20 первым. Полный вызов из локальной среды занял 6909 мс, поэтому сокращение SQL ещё не означает устранение сетевой задержки. Проверка прав: security_definer=false, service_execute=true, anon_execute=false, authenticated_execute=false. Пустой и односимвольный запрос дали 0 строк, match_count=1000 ограничен 50 строками.

TypeScript, ESLint, search-source-recovery regression suite, все prebuild guards и полная Next production сборка прошли. Браузерный first-result и production lexicalMs после выкладки нового приложения ещё не измерены.
