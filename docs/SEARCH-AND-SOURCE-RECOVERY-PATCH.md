# AnimeBox: ТЗ на ускорение поиска и достоверную доступность источников

## 1. Задача

Уменьшить повторную серверную работу при поиске и восстановить проверку серий при недоступной внешней карточке аниме. Пользователь должен различать отсутствие конкретной серии, незавершённую проверку, тайм-аут и ограничение доступа. Результаты должны оставаться привязанными к правильному тайтлу и выбранной серии.

Работа выполняется поверх main 1e3f0ad0d629d06ffff3fdf84448a081dcb4db69. Хост приложения — Railway, изображения — существующий media pipeline. Не менять DNS, хостинг, базу, ключи, платёжную систему и player iframe API.

## 2. Исходные доказательства

Публичные проверки 6 октября 2026 до изменения:

| Запрос | Ответ | Полное время |
| --- | --- | --- |
| Kodik Frieren, MAL 52991, серия 1 | available, 33 озвучки | 5,33 с |
| Kodik Naruto, MAL 20, серия 1 | available, 5 озвучек | 5,55 с |
| Kodik Naruto (2026), MAL 54688, серия 1 | unavailable, 0 озвучек | 5,57 с |
| Frieren episode-availability, AniList 154587 | unknown, providers пустой | 11,46 с |
| instant search naruto, limit 18 | 17 карточек, tookMs 2299 | 7,96 с |
| повтор instant search naruto | 17 карточек, tookMs 2337 | 6,67 с |
| основной search naruto | 11 карточек | 6,98 с |

Прямой read-only RPC search_anime_hybrid_lexical_v2 с match_count=40 вернул 40 строк без ошибки, но из среды проверки занял 8946 мс. Эти времена относятся к конкретным запросам и сети среды проверки. Они не являются медианой, измерением CPU, LCP или скоростью всех посетителей.

Нельзя заключить, что Kodik сломан для большинства аниме: проверены лишь несколько тайтлов. Отсутствие первой серии у одного релиза не доказывает отсутствие всего тайтла у всех провайдеров. unknown с пустыми providers у Frieren при успешном прямом Kodik показывает разрыв проверки, но не раскрывает исходную серверную ошибку без логов.

## 3. Причины на уровне кода

### Проверка серий

В опубликованной старой ветке episode-availability использовался AniList detail; в локальной рабочей версии уже был resolveAnimeRoute с fallback. Оба пути могут ждать внешние метаданные до обращения к провайдерам. Для Kodik нужен прежде всего подтверждённый MAL/Shikimori ID, который уже хранится в локальном каталоге.

catch маршрута возвращал unknown без причины. В UI итоговая причина выбиралась по последнему резервному источнику. Последнее not_found могло скрыть предыдущий provider_timeout и дать сообщение «серии нет», хотя проверка другого провайдера не завершилась.

### Поиск

Клиент запускает instant preview параллельно основному /api/anime. Оба используют searchLocalAnimeIndex, но разные limit порождают разные match_count. Повторяются близкие RPC-пулы. Объединения RPC между запросами не было.

Instant route сначала проходит защиту API, затем выполняет локальный поиск и фильтрацию availability. Прежний tookMs измерял только этап после rate limit. Поэтому разность полного сетевого времени и tookMs нельзя полностью приписывать внешнему поиску.

Клиентский кеш сохранял пустые instant ответы на три минуты. Сервер использует такой же пустой успешный payload при ошибке локальной быстрой ветки; восстановившийся индекс мог остаться скрыт за негативным кешем.

## 4. Контракты и неизменяемые правила

- AniList ID остаётся внутренним ID. MAL ID не подменяет его.
- Kodik ищется по подтверждённому idMal/mal_id.
- Не искать произвольный одноимённый релиз и не выдавать его вместо правильного сезона.
- episode_unavailable означает отсутствие выбранной серии по завершённой проверке, а не любую сетевую ошибку.
- unknown не превращать в unavailable.
- Сохранить copyright 451, provider controls, rate limits, half-open recovery, серверную проверку и общий ограниченный бюджет discovery.
- Не объявлять непроверенные локальные hits playable. Availability filtering остаётся на каждом ответе instant route.
- Не кешировать личные рекомендации, авторизацию и ответы с секретами.
- Сохранить сортировку поиска, keyboard/transliteration fallback и пагинацию.

## 5. Реализация серверного поиска

Создать lib/public-result-cache.ts — небольшой процессный кеш только публичных результатов.

| Параметр | Значение для lexical lookup |
| --- | --- |
| TTL | 30 секунд |
| Максимум завершённых ключей | 128 |
| Максимум ожидающих ключей | 128 |
| Кеширование пустого результата | Нет |
| Кеширование исключения | Нет |
| Поведение при переполнении pending | Выполнить запрос без сохранения |

Для совпадающего ключа ожидающие клиенты получают один Promise. Очистка pending всегда в finally. Срок начинается после завершения загрузки. Просроченный ключ удаляется при чтении, cardinality ограничена вытеснением старых ключей. Кеш не общий между контейнерами и теряется при рестарте.

В runLexicalSearch привести match_count к ближайшему большему десятку с максимумом 40. Например, limit 16 даёт исходный пул 32, limit 18 — 36; оба используют RPC pool 40. Ключ — JSON массива [query, poolSize]. Разные текстовые варианты не смешивать. Каждый вызывающий searchLocalAnimeIndex по-прежнему сортирует и обрезает свой результат до собственного limit.

RPC loader сохраняет существующий fallback с hybrid lexical v2 на legacy только при отсутствии функции. Ошибочные/пустые результаты не сохранять. Это оптимизация количества запросов, а не изменение схемы или новая SQL-функция.

Риск: увеличенный пул может добавить кандидатов при fuzzy lookup, что допустимо при сохранённом scoring. TTL может задержать появление только что проиндексированного документа до 30 секунд. Availability продолжает проверяться отдельно, поэтому lexical кеш не является разрешением на просмотр.

## 6. Тайминги поиска и Kodik

Instant JSON дополнить timings: rateLimitMs, lexicalMs, availabilityMs. Сохранить существующий tookMs для совместимости. Добавить отдельные Server-Timing метрики для этих этапов.

Успешный Kodik response дополнить Server-Timing: rate limit, provider lookup, полная длительность handler. Не выводить токен, URL API с токеном, user ID, cookies или содержимое переписки. Время SQL/сети/CPU здесь не разделяется; метрики измеряют ожидание этапа целиком.

Rate-limit проверку не отключать, не кешировать её разрешение и не увеличивать пределы ради улучшения графика скорости. Эти измерения нужны, чтобы после деплоя отличить защиту API от provider lookup.

## 7. Быстрый путь проверки доступности

Маршрут /api/anime/{numericId}/episode-availability:

1. Сохранить валидацию положительного целого ID.
2. Получить getLocalAnimeDetailFallback(animeId).
3. Если локальная карточка содержит MAL mapping, использовать её для провайдерной проверки без resolveAnimeRoute.
4. Если карточки/mapping нет, сохранить resolveAnimeRoute fallback для неизвестных локальной базе тайтлов.
5. При отсутствии карточки вернуть существующий 404.
6. Сохранить 8-секундный signal провайдерного этапа и отмену request.
7. Сохранить SEO index sync в after только при подтверждённых эпизодах.
8. На исключении вернуть unknown и optional reason: provider_timeout для TimeoutError/AbortError, availability_check_failed для других исключений.
9. Сохранить короткие TTL для unknown и более длинные для available/unavailable.

Быстрый путь использует сохранённые данные и может ждать Supabase. Он не доказывает отсутствие всех сетевых задержек и не отменяет fallback для отсутствующего mapping. Отдельные провайдеры уже могут вернуть unknown с собственной reason; не переписывать их в unavailable.

## 8. Достоверная итоговая причина в плеере

Создать pure helper sourceFailureReason(reasons, budgetExpired). В AnimeEpisodePage собрать причины всех неуспешных попыток и использовать helper для финального сообщения вместо последнего результата.

Порядок:

1. Общий истёкший бюджет → discovery_budget_exhausted.
2. Хотя бы один provider_timeout → provider_timeout.
3. Любая неопределённая/ошибочная причина → сохранить её вместо not_found.
4. Только copyright_restricted во всех попытках → copyright_restricted.
5. Завершённые not_found/episode_unavailable/direct_stream_not_found → сообщение об отсутствии серии.
6. Нет пригодных причин → no_playable_source.

Успешный источник по-прежнему публикуется и открывается сразу. Background warm fallback, порядок провайдеров, интервалы, fullscreen, postMessage, античит и tracker не меняются. Тайм-ауты не увеличивать без данных о конкретном provider: увеличение ожидания само по себе не устраняет первопричину.

## 9. Клиентский поиск

В instant-search-client сохранять в memory cache только непустые результаты. Ошибка instant ветки не блокирует основной поиск; основная ветка остаётся авторитетной для финального ранжирования и страниц. Действующие request abort/sequence guards сохраняются.

Не вводить ложную страницу результатов через произвольный fallback. Не менять текст ввода после ответа. Не обещать время меньше секунды: первый RPC, сеть и другие этапы требуют измерений после деплоя.

## 10. Регрессионная проверка

tests/search-source-recovery.mjs проверяет:

- один loader для двух одновременных ключей;
- повторное чтение до TTL без loader;
- повторную загрузку после TTL;
- bounded completed cache и overflow pending;
- повтор после исключения;
- отсутствие негативного кеша пустого результата;

- provider_timeout не скрывается последующим episode_unavailable;
- provider_unavailable не скрывается not_found;
- сохранение чистого отсутствия серии, copyright и общего budget failure;
- реальный episode-availability route с fixture: saved mapping пропускает external detail resolver;
- fallback resolver вызывается при отсутствии локальной карточки;
- timeout остаётся unknown с reason;
- некорректный numeric ID возвращает 400.

Запуск:

## 14. Проверка собранного приложения с реальной базой

Собранный Next production сервер запускался локально с существующей базой и переменными окружения. Первый instant naruto: HTTP 200, 17 карточек, 18069 мс всего; rateLimitMs=6003, lexicalMs=7241, availabilityMs=4487. Повтор: HTTP 200, те же 17 карточек, 5130 мс всего; rateLimitMs=5117, lexicalMs=1, availabilityMs=0. Это подтверждает устранение повторной lexical работы в одном процессе, но также показывает оставшийся медленный rate-limit RPC из среды проверки. Не экстраполировать эти времена на Railway без повторного замера.

Локальный Frieren episode-availability вернул HTTP 200, status=unknown, reason=provider_timeout за 11762 мс. Корректная причина теперь видна, однако успешная доступность провайдера в этом окружении НЕ подтверждена. Исправление fallback не следует объявлять полным восстановлением всех источников.

После этого замера обнаружены повторные одновременные чтения Player Source Control: getProviderDecision для Kodik и AniLiberty независимо загружали одну settings/runtime пару. Добавлен общий in-flight Promise для этой пары. Существующий кеш 15 секунд и admin invalidation сохраняются; результат ошибки не становится постоянным кешем. Тест реального control module с fixture проверяет одну пару чтений вместо двух, warm hit и reload после invalidation. Этот дополнительный код проверяется новой финальной сборкой; приведённые локальные тайминги получены ДО объединения control reads.

Отдельный следующий этап — замер rate-limit RPC и provider policy на Railway, проверка сети/региона и подтверждённых пользовательских тайтлов. Защита API в этой поставке не ослабляется.
