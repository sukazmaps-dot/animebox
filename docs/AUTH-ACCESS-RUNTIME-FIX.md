# AnimeBox: вход и доступность после переезда на Railway

Дата: 10 октября 2026. База: main после PR #184.

## 1. Цель и критерий результата

Пользователь открывает youranimebox.com, входит выбранным способом, возвращается на публичный сайт и видит свой профиль. Служебный URL контейнера никогда не попадает в Location callback. При сбое Telegram запрос заканчивается объяснимой ошибкой, а повторная попытка остаётся доступной. Проверка изображений отличает настоящий постер от HTTP-успеха без изображения.

Кодовая часть и проверка инфраструктуры имеют отдельные критерии готовности. Пройденный build не подтверждает регистрацию webhook у Telegram или вход в реальном аккаунте. Готовность полного пользовательского пути требует ручного входа и проверки в Mini App.

## 2. Доказательства до изменения

### 2.1. Ошибка callback подтверждена в production

Запрос без OAuth-кода, не меняющий состояние аккаунта:

```bash
curl -sS -D - -o /dev/null 'https://youranimebox.com/auth/callback?next=%2Flist'
```

Фактический результат до патча:

```text
HTTP 307
Location: https://localhost:8080/login?error=google-auth
```

Сервер формирует request.url из адреса за reverse proxy. В app/auth/callback/route.ts этот origin использовался для всех возвращаемых Location. Значит, ошибка затрагивала не только невалидную ссылку, но и адрес назначения при успешном обмене кода, onboarding и восстановлении пароля. Успешный вход отдельным живым аккаунтом до патча не выполнялся.

### 2.2. Публичные настройки входа доступны

/api/auth/config возвращает непустые Google и Telegram Client ID. Это исключает отсутствие этих публичных полей как причину проверенного запроса. Наличие Client ID не подтверждает настройки разрешённых доменов у провайдера и успешность проверки подписанного токена.

### 2.3. Media health не доказывает доставку обложки

Проверена обложка AniList, присутствующая в HTML главной:

```text
https://s4.anilist.co/file/anilistcdn/media/anime/cover/large/bx154587-qQTzQnEJJ3oB.jpg
```

Для /api/image получен декодируемый JPEG 460×649, 136267 байт. Для media Worker в тот же период получены HTTP 204, X-AnimeBox-Media: source-soft-fail и X-AnimeBox-Origin-Error: origin-403. Это означает отказ источника для маршрута Worker. Причина блокировки у внешнего CDN не установлена. Не следует считать все источники или все регионы недоступными по одному образцу.

### 2.4. CSP

Публичный ответ содержит Content-Security-Policy: frame-ancestors 'none';. Эта директива не запрещает eval. В прикладном коде не обнаружен очевидный вызов eval/new Function для пользовательского исполнения. Использование new Function в Node-тестах не является браузерным исполнением. Точный скрипт, породивший сообщение DevTools, пока не установлен.

## 3. Требования к callback

### 3.1. Политика адреса

- В production всегда использовать https://youranimebox.com из существующего реестра SITE_URL.
- Определять production существующим isProductionDeployment, включая Railway без VERCEL_ENV.
- В Vercel Preview сохранять origin preview-запроса.
- В локальной разработке сохранять localhost и порт запроса.
- Не использовать Host, X-Forwarded-Host или X-Forwarded-Proto как произвольное основание для адреса возврата.
- Значение next продолжать обрабатывать safeInternalPath.
- Отбрасывать внешний next, протокол-relative //host и варианты с обратным слешем.
- Сохранять query и fragment допустимого внутреннего пути.

### 3.2. Ветки результата

| Сценарий | Production Location |
|---|---|
| Код обменян, профиль с username | Канонический домен + безопасный next; по умолчанию /profile |
| Код обменян, username отсутствует | /onboarding?next=… на каноническом домене |
| Recovery code | /auth/update-password на каноническом домене |
| Recovery token_hash | /auth/update-password на каноническом домене |
| Нет необходимых параметров | /login?error=google-auth либо invalid_recovery |
| Ошибка обмена кода | Соответствующая страница ошибки на каноническом домене |
| Сессия не создана | Страница ошибки; не перенаправлять в защищённый профиль |
| Проверенный пользователь отсутствует | /login?error=google-auth |

### 3.3. Сессии и кеш

- Сохранить существующие exchangeCodeForSession и verifyOtp.
- Сохранить проверку пользователя через getUser.
- Не вводить доверие к клиентскому user_metadata или неподписанным cookie.
- Не менять формат сессии, RLS и схему БД.
- Callback должен быть force-dynamic.
- Каждый redirect должен включать Cache-Control: private, no-store и CDN-Cache-Control: no-store.
- В next.config.ts добавить точное правило /auth/callback после широкого /auth/:path*: реальный production smoke показал, что широкое правило перезаписывает Cache-Control redirect, несмотря на правильный заголовок в route handler. Точное правило сохраняет private, no-store на фактическом ответе.
- Существующий SSR cookie adapter остаётся ответственным за запись cookie.
- Реальный Set-Cookie и повторный запрос с сессией проверяются отдельно на действующем входе; mock не заменяет эту проверку.

## 4. Требования к Telegram

### 4.1. Ограниченные сетевые ожидания

- Получение nonce: максимум 15 секунд для сетевого запроса.
- Отправка подписанного id_token на сервер: максимум 15 секунд.
- Timeout/Abort показывать как понятную ошибку с возможностью повторить.
- Сохранить nonce, его узкий cookie path, HttpOnly, SameSite и одноразовое использование.
- Не ослаблять JWT-проверку issuer, audience, подписи и nonce.
- Не подменять проверку Mini App initData доверенным JSON-профилем.
- Не ограничивать пользовательское время подтверждения в окне OAuth этим сетевым таймаутом.
- Убрать текст ошибки, направляющий пользователя к Vercel Logs при работающем Railway.
- В ответе /animebox_chat_id использовать нейтральное указание на переменные сервера, без привязки к Vercel.
- sendMessage webhook ограничить 10 секундами; при ошибке сохранить существующий ответ ошибки, чтобы Telegram мог повторить доставку.
- Не вводить автоматические повторные отправки sendMessage: это способно создать дубликаты.

### 4.2. Проверка зарегистрированного webhook

Добавить scripts/telegram-webhook-ops.mjs:

- По умолчанию только getWebhookInfo.
- Токен читать из TELEGRAM_BOT_TOKEN; не принимать в аргументах командной строки.
- В stdout выдавать только признаки конфигурации, число ожидающих обновлений, время записанной ошибки и список подписанных типов updates.
- Не печатать URL Telegram API с токеном, секрет, сырые описания ошибок или URL старого webhook с возможными чувствительными параметрами.
- Ошибки fetch санитизировать: сообщение может содержать токенизированный URL.
- При --apply проверять формат webhook secret по требованиям Telegram.
- Перед setWebhook отправить пустой подписанный update {} на канонический endpoint. Он не содержит chat/message/payment и не отправляет сообщения пользователям.
- Если endpoint не принимает текущий secret, остановиться до изменения Telegram.
- Установить только https://youranimebox.com/api/telegram/webhook.
- Сохранить pending updates: drop_pending_updates=false.
- Сохранить existing allowed_updates, в том числе подписки Stars, если они указаны в getWebhookInfo.
- После изменения повторить getWebhookInfo и проверить точное совпадение URL.
- Режим --apply не запускать автоматически при build, CI или старте сервера.
- Не регистрировать webhook при каждой реплике Railway: это вызывает гонки конфигурации.

Команды в окружении, где секреты уже настроены:

```bash
npm run telegram:webhook:check
npm run telegram:webhook:check -- --apply
```

Вторая команда изменяет регистрацию webhook. Она нужна только при подтверждённом несовпадении адреса или секрета. В этой работе реальная регистрация не менялась: production bot credentials в рабочем окружении отсутствуют.

## 5. Требования к проверке постеров

Добавить scripts/media-poster-smoke.mjs:

- Принимать от одной до шести явных публичных HTTPS-ссылок обложек.
- Не принимать userinfo в URL.
- Для каждой ссылки проверять media /image?w=360&q=70&f=webp и канонический /api/image.
- Не обращаться к внешнему источнику напрямую из проверочного скрипта.
- Таймаут каждого маршрута — 20 секунд.
- Redirect запретить: неизвестный промежуточный маршрут не должен скрывать поломку.
- Обязателен успешный HTTP-ответ и растровый MIME.
- SVG-заглушки, HTML, пустое тело, 204, повреждённое изображение не считать успехом.
- Максимум ответа — 8 MiB; ограничивать поток, а не только Content-Length.
- Ограничить декодирование 16 миллионами пикселей.
- Проверять не только metadata, но и фактическое декодирование пикселей.
- Проверять соответствие MIME фактическому формату.
- Выводить размеры, формат, размер файла, статус маршрута и диагностические заголовки Worker.
- Вернуть ненулевой exit code, если хотя бы один маршрут не доставляет реальный постер.
- Не запускать сетевой smoke внутри prebuild: внешняя доступность не должна определять воспроизводимость сборки.

```bash
npm run media:poster:smoke -- 'https://s4.anilist.co/file/anilistcdn/media/anime/cover/large/bx154587-qQTzQnEJJ3oB.jpg'
```

Матрица живой приёмки должна включать AniList, актуальный Shikimori .io и один резервный источник. Успех одной обложки не распространяется на весь каталог.

Дополнительно исправить обнаруженный кодовый дефект: вторичный Shikimori source в смешанной цепочке AniList → Shikimori ранее добавлялся как прямая browser-ссылка. Каждый вторичный Shikimori .io/.one/.me должен проходить через /api/image. Для пары Shikimori original/preview сохранить обе доступные серверные попытки. Не менять приоритет media Worker и не увеличивать число источников. Worker в этом патче не меняется. Обход origin-403 через Railway как новый Worker upstream требует отдельной оценки нагрузки, бюджета времени и политики кеша; без этой оценки включать такой маршрут нельзя.

## 6. CSP: порядок диагностики

- Получить URL скрипта и точный стек ошибки из чистого браузера без расширений.
- Проверить основной документ и iframe отдельно: iframe имеет собственную CSP.
- Сопоставить заголовки ответа с настройками Cloudflare и стороннего провайдера.
- Проверить успешный вход и плеер независимо от сообщения Issues.
- Не добавлять unsafe-eval или широкое разрешение script-src без доказанной потребности.
- Не считать ERR_BLOCKED_BY_CLIENT от рекламного домена ошибкой AnimeBox.
- Не объявлять CSP исправленной до воспроизводимого сценария и проверки.

## 7. Автоматические проверки

### 7.1. Callback — исполнение настоящего route handler с моками зависимостей

- Внутренний Railway URL и production без VERCEL_ENV.
- Подделанные forwarded headers не меняют адрес назначения.
- Безопасный next с query.
- Внешний next и обратный слеш.
- Новый пользователь и onboarding.
- Recovery через code и token_hash.
- Нет кода, ошибка обмена, отсутствующая сессия, отсутствующий user.
- Cache-Control и CDN-Cache-Control каждого redirect.
- Preview и localhost не переезжают на production домен.

### 7.2. Операционные инструменты

- Read mode вызывает только getWebhookInfo.
- --apply сначала проверяет endpoint, потом меняет webhook, потом перечитывает состояние.
- Отклонённый secret не приводит к setWebhook.
- Очередь updates и subscribed types сохраняются.
- Ошибка сети не раскрывает токен.
- Настоящий PNG декодируется; HTML/SVG/повреждённый JPEG/ложный MIME/HTTP 502 отклоняются.
- Оба маршрута изображения получают один и тот же source URL.
- Смешанная цепочка AniList → Shikimori и пара Shikimori original/preview не содержат прямых Shikimori browser-URL.

### 7.3. Проверки проекта

- npm run auth-access:check — новые проверки в CI и prebuild после release-consolidation.
- npx tsc --noEmit.
- ESLint изменённых файлов.
- npm run browser-session:check, если скрипт доступен, и существующие browser-request-origin/public-auth-config тесты.
- npm run schedule-media:check — существующие SSRF, allowlist, ограничение тела и резервные изображения.
- npm run build — все обязательные существующие gates и production build.

## 8. Живая приёмка после выпуска

1. Повторить безкодов callback probe: Location должен вести на публичный домен.
2. Открыть вход в обычном браузере и в приватном окне.
3. Google: действующий профиль → next; новый профиль → onboarding.
4. Telegram: подтверждение, отмена, повторная попытка, восстановление после сетевого сбоя.
5. Recovery email: действующая и просроченная ссылки; новый пароль; повторный вход.
6. Проверить сессию после обновления страницы и перехода в /list.
7. Mini App: вход по initData, выход, повторное открытие; OAuth popup внутри Mini App не открывается.
8. Bot: getWebhookInfo, затем ручной /start от владельца и переход по меню. Проверить исчезновение растущей очереди updates.
9. Проверить живые постеры и fallback на карточке, в расписании и на странице тайтла.
10. Сверить CSP только после установления источника сообщения.

## 9. Выпуск и откат

Патч публикуется отдельной веткой/PR. БД-миграции и новые переменные окружения не требуются. Изменение callback не требует обновления Cloudflare Worker. После согласованного выпуска main запускает существующее развёртывание Railway.

При проблеме код откатывается отдельным revert. Если применялся --apply, регистрация Telegram является отдельным состоянием и не откатывается git revert; вернуть webhook к прежнему рабочему адресу с правильным secret без очистки очереди.

## 10. Границы утверждений

Подтверждены callback на localhost и разница доставки одного реального постера между Worker и /api/image. Не подтверждены фактическая конфигурация Telegram webhook, успешный OAuth живого аккаунта, визуальный результат в браузере и источник CSP eval. Эти пункты нельзя помечать выполненными только по unit-тестам или успешной сборке.

## 11. Промежуточная проверка реализации

- Новые тесты callback и операционных инструментов прошли.
- Существующие browser-request-origin, public-auth-config и schedule-media проверки прошли.
- TypeScript: ошибок не обнаружено.
- ESLint: 0 ошибок; существующее предупреждение о неиспользуемом _malId в image-service.
- Первая полная сборка остановилась из-за повреждённого локального .next/Turbopack cache. После удаления только кеша сборки полный npm run build прошёл.
- После последней правки вторичного Shikimori повторные regression tests и финальный полный npm run build прошли. Старый static gate обновлён с прямого secondary на secondaryFallback; поведенческий тест проверяет запрет прямого Shikimori.
- Production webhook без секрета возвращает HTTP 401 unauthorized: endpoint доступен, отсутствие подписи отклоняется. Это не доказывает состояние getWebhookInfo.
- Настройки Telegram и Supabase в production не менялись; реальные сообщения и платежи не отправлялись.

Справочные первичные источники: https://supabase.com/docs/guides/auth/server-side/creating-a-client и https://core.telegram.org/bots/api#getwebhookinfo.

Финальная проверка собранного production-сервера: callback вернул HTTP 307, Location https://youranimebox.com/login?error=google-auth, Cache-Control private, no-store и CDN-Cache-Control no-store. Проверен настоящий Next.js сервер, а не только mock route handler. Финальный полный build после точного callback header rule также прошёл.
