# AnimeBox: ТЗ на патч проверки скорости и устойчивости первого экрана

## 1. Цель и границы

Проверить опубликованные изменения главной и чата на Railway, получить воспроизводимый исходный отчёт и устранить подтверждённые ошибки начальной загрузки. Пользовательский сценарий: гость открывает сайт, получает первые карточки, переходит в аниме, открывает расписание и общий чат. Отдельная ветка — доступность страницы входа и дальнейшая проверка Google/Telegram.

Поставка включает автоматический HTTP-аудит, исходный отчёт, исправление восстановления групп главной и регрессионные проверки. Не вводить новые платные сервисы, зависимости, миграции, фоновые задания или изменения DNS. Не менять персональное ранжирование, правила доступности аниме, авторизацию и модерацию чата.

## 2. Что уже внедрено

- Первый экран получает сохранённые проверенные карточки, когда они доступны.
- Проверенный feed кешируется на 300 секунд.
- Чат отдаёт оболочку через Suspense до завершения истории.
- Realtime сообщение не ждёт оформление автора.
- История восстанавливается клиентом после пустого начального ответа.

Эти изменения не повторять. Проверить результат и обработку отказов. Исходный опубликованный commit: b7617a22f6b0e0df9dae4a5bc02352edad88c92f.

## 3. Вопросы, которые должен разрешить аудит

1. Доступны ли публичные маршруты на текущем хосте?
2. Отдаёт ли каталог массив карточек, а расписание массив событий?
3. Сколько занимает получение заголовков и полного HTML/JSON?
4. Отличается ли повторный проход от первого?
5. Что происходит с доступной группой главной при отказе другой?
6. Продолжает ли чат отдавать оболочку до задержанной истории?
7. Какие проверки остались без доказательств и почему?

## 4. Воспроизводимый HTTP-аудит

Файл: scripts/public-performance-audit.mjs. Запуск:

```bash
node scripts/public-performance-audit.mjs https://animebox-production.up.railway.app docs/PUBLIC-PERFORMANCE-BASELINE.json
```

### Маршруты

| Маршрут | Проверка |
| --- | --- |
| /api/anime?limit=1 | HTTP, JSON, массив anime, число результатов, источник fallback при наличии |
| / | HTML главной, время заголовков и завершения, размер тела |
| /search | HTML каталога/поиска |
| /anime/{slug} | Реальный slug из ответа каталога, без выдуманного ID |
| /chat | HTML маршрута и продолжительность stream |
| /schedule | HTML страницы расписания |
| /login | Доступность страницы входа |
| /api/schedule?limit=60 | JSON, массив items и число событий |

### Порядок и ограничения

- Сначала получить одну карточку для выбора существующего маршрута аниме.
- Выполнить два последовательных прохода остальных маршрутов.
- Не создавать параллельную нагрузку и автоматические повторы.
- Ограничить каждый запрос 20 секундами, включая чтение тела.
- При ошибке записать результат и продолжить другие независимые маршруты.
- Возвращать ненулевой exit code, если хотя бы одна проверка невалидна.
- Отчёт не содержит тела переписки, токенов, cookies, email и переменных окружения.
- Сохранять только публичный origin, маршруты и технические показатели.

### Поля результата

- status: HTTP-код.
- headersMs: время от старта fetch до получения заголовков; это не браузерный TTFB.
- totalMs: время до завершения чтения ответа.
- bytes: объём декодированного тела, а не размер передачи по сети.
- contentType, cacheControl, cacheStatus: наблюдаемые заголовки.
- count: число объектов в API; пустой массив может быть корректным.
- valid: транспортный статус и ожидаемая структура.
- scripts/images: число тегов HTML; это не стоимость JS и не число сетевых запросов.
- pass: номер прохода. Не называть их гарантированными cold/warm: состояние upstream/CDN кешей неизвестно.

## 5. Браузерная матрица

Проверить viewport 390×844 и 1440×900. Для каждого — новое открытие и возврат, обычная сеть и одинаковый выбранный профиль throttling. Для сравнения скорости использовать минимум три повтора в одинаковых условиях и медиану; два HTTP-прохода служат только smoke baseline.

Фиксировать LCP, CLS, длительность длинных задач, загрузку JS/изображений, ошибки консоли, неудачные запросы, время первого видимого ряда и сообщений. INP измерять при реальных действиях; не объявлять его проверенным по загрузке страницы. Эмуляция viewport не заменяет физический телефон.

### Главная

Проверить появление первых карточек, отсутствие пустых рядов при доступной базе, устойчивость порядка при прокрутке, догрузку вправо, переход в тайтл и возврат. Не включать priority для всех постеров ради формального уменьшения одного ожидания.

### Каталог и карточка

Проверить ввод поиска, фильтр и догрузку. Отдельно сверить название, постер, описание, формат, год, серии и студию с наличием полей в API. Не заполнять отсутствующие сведения выдуманными значениями. Проверить открытие существующего slug.

### Чат

Проверить оболочку, первую историю, подключение Realtime, старую историю, сохранение положения прокрутки. Проверки отправки, реакций и удаления выполнять только в согласованном тестовом сценарии с учётной записью; публичная доступность HTML не доказывает их работу.

### Авторизация

Проверка /login подтверждает только страницу. Для Google нужен фактический проход Google Sign-In → Supabase session → профиль; для Telegram — окно провайдера → серверная проверка → session → профиль. Не считать HTTP 200 доказательством регистрации.

Проверить наличие настроек сборки NEXT_PUBLIC_GOOGLE_CLIENT_ID и NEXT_PUBLIC_TELEGRAM_CLIENT_ID без вывода значений. Для ошибок origin сверить фактический публичный адрес с настройками провайдеров. Не менять callback наугад: текущий Google использует ID token, а Telegram привязан к origin. Успешный вход и действия, требующие владельца, отмечать отдельно от проверки гостем.

## 6. Подтверждённая ошибка и исправление

В lib/home-feed-server.ts две группы загружались Promise.all внутри unstable_cache. Отказ внешней ветки ongoing приводил к выходу в catch getHomeInitialFeed, возвращавшему пустые popular и ongoing. Сохранённые популярные карточки тоже исчезали.

Исправление: в catch независимо прочитать saved каталог для ranked и popularity/status ongoing. Вернуть каждую доступную группу; ошибка одной recovery-загрузки превращает только её в пустой массив. Выполнять восстановление вне unstable_cache: частичный аварийный ответ не кешируется на пять минут, следующий вызов снова пытается заполнить здоровый кеш.

Использовать существующую playable view, лимит 12, страницу 1 и существующие фильтры. Не возвращать внешние непроверенные карточки при отказе registry. Не запускать повторно внешние API в recovery. Не менять ключ кеша: структура успешного ответа осталась прежней, аварийная ветка вне кеша.

Ограничение: при сбое добавляются до двух запросов сохранённого каталога. Исправление сохраняет данные, но не устраняет задержку ожидания исходного отказа и не гарантирует мгновенного ответа базы.

## 7. Проверки реализации

1. tests/public-performance-audit.mjs поднимает локальный HTTP fixture: корректный каталог, пустое расписание, некорректный JSON, зависший запрос и HTML. Проверить структуру, timeout и показатели.
2. tests/home-verified-cache.mjs воспроизводит частичный сбой: ranked сохранён, ongoing provider падает. Ожидать непустой popular и пустой ongoing.
3. После восстановления провайдера следующий вызов возвращает ongoing: аварийный partial не отравил кеш.
4. Сохранить проверки healthy warm cache, обхода внешнего API для saved и восстановления после отказа registry.
5. tests/chat-streaming-bootstrap.cjs проверяет реальный server route с задержанной историей: оболочка до данных, сообщения после.
6. TypeScript и ESLint изменённых файлов без ошибок.

## 9. Приёмка и выпуск

- Автоматический аудит воспроизводим отдельной командой без секретов.
- Структурные ошибки и зависания отражаются как провал, а не теряются.
- При частичном отказе главная сохраняет доступную saved группу.
- При следующем здоровом запросе нормальное заполнение кеша восстанавливается.
- Никаких изменений в OAuth, player, персональных данных и схеме БД.
- В GitHub публикуются только перечисленные файлы патча, без локальных изменений Cloudflare и зависимостей.
- После Railway redeploy повторить аудит тем же origin и сравнить условия. Не обещать скорость до повторного измерения.
- Для отката вернуть lib/home-feed-server.ts к предыдущему commit; аудит и документы могут остаться. Миграций для отката нет.

## 10. Следующий этап по результатам

Приоритет — локализовать задержку главной с cache HIT. Только после этого выбирать streaming главной, изменение кеша, оптимизацию saved SQL или региона. Следом — браузерная проверка первой загрузки постеров и авторизации. Не смешивать эти гипотезы с подтверждённой ошибкой очистки групп.
