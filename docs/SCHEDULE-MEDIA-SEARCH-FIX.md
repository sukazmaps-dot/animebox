# Комплексный патч: постеры расписания, полный поиск, Telegram и иконки

Ветка: `fix/schedule-media-search-ui`. Основа: main `85d86453ed95144cb13ab058b9cb9b289dee0e45`, независимо от PR #182.

## Найденные причины

1. `lib/shikimori-metadata.mjs` нормализует относительные постеры в `https://shikimori.io/...`. `/api/image`, Cloudflare Worker и RU media разрешают `.me`/`.one`, но не `.io`: один корректный источник превращается в 403 на сайте и 400 на media. Затем клиент пробует прямой Shikimori, где возникает connection reset. User-Agent уже присутствует, но Referer настроен только для старых доменов.
2. `/api/image` возвращает 204 без тела при отказе источника: браузеру нечего декодировать. Фикса только catch недостаточно — нужно синхронизировать домены, нормализацию, редиректы, MIME и fallback chain.
3. `public/brand/favicon.png` повреждён: полноценный PNG-декодер получает `Truncated File Read`. Объявленные 192×192 совпадают лишь с заголовком; файл нельзя считать исправным по расширению или первому байту. Есть целые брендовые PNG/WebP в репозитории.
4. Telegram-карточка собирается из конкурирующих глобальных CSS: двухколоночный vector layout, старые размеры контента, footer `height:100%`, compact padding и overflow hidden. Исправление должно принадлежать компоненту, а не ещё одному глобальному слою с !important.
5. Полный поиск ждёт внешний провайдер, затем сохранённую view. View `anime_saved_playable_catalog` создаётся отдельным SQL-файлом, а не обязательной текущей миграцией. Недоступность view/новых столбцов может уничтожить резервный путь, хотя локальный индекс работает. Дополнительный запрос smart fallback тоже способен отменить уже найденные результаты.
6. Подробная техническая оговорка Shikimori выводится отдельным большим абзацем, а само расписание уже помечает плановые события. Пользователю достаточно короткой подписи и сообщения только о реальной задержке обновления.

Наличие этих дефектов в коде подтверждено. Конкретный production SQL/HTTP-сбой поиска без серверных журналов остаётся неподтверждённым; исправляем перечисленные пути отказа и проверяем их отдельно.

## 1. Единая политика внешних изображений

- Добавить точный `shikimori.io` и его поддомены в три существующих media-обработчика. Не добавлять произвольные домены, localhost, IP, credentials или нестандартные порты.
- URLSearchParams декодирует query один раз. Дополнительное декодирование допустимо только для целиком закодированного URL, максимум два шага. Уже корректный URL с `%2F`, query-параметрами или подписью не декодировать повторно.
- Разрешить HTTPS и protocol-relative provider URLs; относительный `/system/...` в серверном proxy нормализовать к Shikimori.io. Проверять каждую цель redirect той же политикой.
- Использовать существующий User-Agent; для `.io` отправлять `Referer: https://shikimori.io/`. Старые `.me`/`.one` сохраняют provider-specific Referer. Не утверждать, что заголовок гарантированно снимает любую upstream-защиту.
- Отказ разрешённого внешнего источника, не-image ответ, слишком большой ответ, timeout/reset и исключение превращать в реальный `public/anime-placeholder.svg`: HTTP 200, `Content-Type:image/svg+xml`, короткий TTL 15 секунд и фиксированный диагностический код.
- Для неправильного/запрещённого входного URL сохранить 400/403. Rate limit сохранить 429/503: placeholder не должен маскировать попытку SSRF или отказ защиты.
- Скачивание ограничить 10 MiB и общим timeout, включая body. Не буферизовать неограниченный upstream.
- Placeholder нельзя кешировать как настоящий постер на месяц. Cloudflare Worker сохраняет существующий soft-fail механизм: его ошибка должна позволять перейти к следующему источнику. Терминальная заглушка принадлежит последнему same-origin proxy.
- Клиент не должен обращаться напрямую к Shikimori после сбоя media: использовать проверенный same-origin proxy. Для AniList/MAL сохранить существующие варианты и лимит кандидатов.
- Проверить все три реализации на совпадение доменов и заголовков. Изменение Worker в GitHub не равно его публикации в Cloudflare; отдельно указать необходимое действие выпуска.

## 2. Полный поиск и сохранённый каталог

- Сохранить быстрый preview, debounce, отмену устаревшего запроса и текущую защиту от перемешивания результатов.
- Ограничить внешнюю фазу полного поиска бюджетом времени и передавать AbortSignal в провайдер. После отказа/таймаута переходить к сохранённым документам; не ждать последовательность длительных внешних retries. Реализованные бюджеты: внешний поиск 4.5 с, каталог 8 с, дополнительная попытка 2 с, вспомогательный локальный поиск 1.5 с, внешняя гидратация локальных совпадений 2 с. Таймаут последней использует уже имеющийся signal; локальный RPC получает ограничение ожидания в API, без изменения shared RPC-контракта.
- Если сохранённая view отсутствует или отстаёт по столбцам, использовать совместимый запрос к существующим search documents и availability. Не добавлять публичные GRANT, не менять RLS, не раскрывать service_role.
- Совместимый путь обязан отфильтровать подтверждённую availability **до** выбора страницы: playable + max_episode>0, сохранение AnimeBox IDs, без подстановки MAL ID в canonical route.
- Читать документы ограниченными пачками, проверять доступность пачкой, не выполнять запрос на каждую карточку. Ввести общий лимит сканирования и timeout. При исчерпании бюджета показать ограничение, не выдавать случайную страницу за полный каталог.
- Реально доступные фильтры выполнять в БД. Если отсутствующие metadata не позволяют точно применить сезон/ongoing/upcoming, вернуть явный unsupported filter, без ложного совпадения и без молчаливого снятия фильтра.
- Ошибка дополнительного smart-search запроса не должна стирать успешные основные результаты. Ошибка локального индекса не должна отменять успешный provider result.
- Сохранённый поиск возвращает HTTP 200 и корректные pagination/catalogMeta, короткий cache TTL. Если недоступны и БД, и провайдер, сохраняется честный 502 и кнопка повтора.
- Не исправлять проблему простым удалением текста «Полный поиск временно недоступен». Он остаётся только при настоящем отказе полного API; штатный saved fallback получает короткое объяснение задержки обновления.
- Никакие новые SQL миграции не обязательны для базового исправления. Расширенная view и metadata sync по-прежнему улучшают полноту; совместимый путь не объявляется эквивалентом всех данных внешнего провайдера.

## 3. Telegram-карточка

- Перенести геометрию компонента в CSS Module, убрать участие старых `telegram-growth-card*` selectors, сохранив название, ссылку, dismiss TTL, Telegram Mini App переход и аналитику.
- Карточка: `position:relative`, `height:auto`, ограничение min-width, рост по содержимому. Не использовать невалидное `min-height:max-content`.
- Content layout: Grid/Flex с `minmax(0,1fr)`, нормальным переносом текста, без absolute для текста и CTA. Кнопка полностью внутри padding, текст CTA переносится, иконка не сжимается.
- Dismiss: absolute top/right 12px, зона нажатия 36–44px, место в верхнем правом углу зарезервировано, focus visible и aria-label сохранены.
- Не влиять на соседние карточки поддержки/трекера. Не ломать mobile 320–430px и Watch Together placement.
- Проверить 320/390/768/1024/1440/1920px, длинные русские строки и увеличенный масштаб текста. Не допускаются overlap, горизонтальный overflow или обрезанная кнопка.

## 4. Иконки

- Заменить повреждённый favicon целым существующим брендированным PNG, сохранив стабильный URL с версией в metadata/manifest для обновления кеша.
- Указать реальный размер нового PNG. Добавить существующий целый WebP 192×192 как второй manifest icon; MIME и размеры должны соответствовать файлам.
- Согласовать `app/manifest.ts` и root metadata. Manifest использует абсолютные пути от корня сайта; не указывать страницу `/` вместо изображения.
- Проверять PNG chunk lengths, CRC, IEND и распаковку IDAT, а не только magic bytes. Проверять фактические размеры каждого объявленного icon.
- Не менять исправный `app/favicon.ico` и не создавать новую графику. Если production отдаёт HTML/redirect/challenge вместо image, это отдельная проблема доставки; проверить после выпуска.

## 5. Расписание без лишнего технического текста

- Убрать постоянный длинный абзац о Shikimori, каталогах и поиске по названию из основного экрана.
- Сохранить `timingKind:planned`, реальные timestamps/timezone и номера серий. Короткая подпись: «Время выхода плановое; озвучка может появиться позже» в раскрываемых подробностях.
- При stale данных показать короткий заметный статус с датой обновления. Не скрывать фактическое устаревание или отказ API.
- Unmapped titles остаются в расписании, а переход по названию ведёт в поиск; не удалять карточки ради отсутствующего постера или canonical ID.
- Постеры из карточек каталога имеют приоритет; Shikimori остаётся корректным резервом. Placeholder применяется только когда настоящая обложка отсутствует/все разрешённые варианты не загрузились.

## 7. Выдача и выпуск

Подготовить PR, этот документ и готовый unified diff по каждому файлу. PNG хранить в GitHub как binary/base64 blob без UTF-8 перекодировки. До выпуска Worker возможно сохранение 400 на media; same-origin fallback обеспечивает резервную доставку, но не означает публикацию нового Worker.
