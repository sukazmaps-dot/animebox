# Аудит языка и правила документации AnimeBox

**Дата аудита:** 22 октября 2026 года  
**Проверенная версия исходного дерева:** `main` на коммите `5088e67dfde3f3940c092a38e1f2727c0594fb02`

## Итог инвентаризации

В дереве репозитория найдено **220 файлов Markdown** общим размером около **1,69 МБ**. Документация неоднородна: основные инструкции уже русские, часть исторических спецификаций смешивает русский текст с английскими заголовками, а некоторые инженерные документы полностью написаны на английском.

Это не 220 равнозначных руководств. В `docs/` накоплен архив планов, требований, результатов проверок и описаний отдельных патчей. Многие из них привязаны к конкретным коммитам или старым состояниям кода. Поэтому нельзя автоматически считать каждую старую инструкцию действующей и нельзя массово удалять либо переименовывать файлы: на них могут ссылаться другие документы, PR и инженерные процессы.

## Принятая языковая политика

1. **Основной язык внутренней документации — русский.** Новые инструкции по запуску, архитектуре, отладке, требованиям к патчам и процессу разработки пишутся по-русски.
2. **Идентификаторы остаются без перевода.** Не переводить имена файлов, функций, типов, CSS-классов, API-маршрутов, переменных окружения, SQL-объектов, названия команд и строки, необходимые для точного поиска по коду.
3. **Кодовые блоки сохраняются дословно**, если это команды, конфигурация, примеры API или программный код. Переводить следует объяснение вокруг них, а не сами исполняемые данные.
4. **Имена файлов пока не менять массово.** Англоязычные пути часто используются в ссылках; перевод содержимого не требует переименования файла. Новые имена выбирать по назначению, без номера патча, когда документ описывает постоянную подсистему, а не историческую работу.
5. **Исторические спецификации не считаются актуальным руководством по умолчанию.** Перед использованием старых команд, SQL или конфигурации нужно сверять сведения с действующим кодом и миграциями.
6. **Статусы реализации не угадывать.** Если разные части документа противоречат друг другу, явно пометить необходимость сверки с кодом и CI вместо того, чтобы произвольно выбрать один статус.
7. **Для внешней международной аудитории** английские версии основных документов можно добавлять отдельно. Это не причина писать внутренние заметки по-английски, если команде удобнее русский.

## Что не переводилось автоматически

- Файлы, состоящие преимущественно из исходного кода, снимков компонентов или больших фрагментов конфигурации. Их перевод не помогает чтению и может случайно изменить исполняемый материал.
- Документация внешних библиотек, официальные спецификации API и тексты, которые нужно цитировать в исходном виде.
- Русскоязычные документы: их повторный перевод не нужен.
- Остальные смешанные/англоязычные архивные документы, которые ещё нужно разобрать по приоритету. Этот этап — целевой перевод обнаруженных инженерных спецификаций, а не заявление о завершённом переводе всех 220 файлов.

## Следующие шаги аудита

1. Пройти оставшиеся документы, начиная с актуальных инструкций запуска, инфраструктуры, выпуска, безопасности и работы новых контрибьюторов.
2. Для старых спецификаций проверять не только язык, но также противоречивые статусы, ссылки, устаревшие команды и расхождения с текущей веткой.
3. Объединять дублирующие инструкции лишь после проверки ссылок и истории; не удалять архивы автоматически.
4. Перед публикацией репозитория отдельно проверить текущие файлы и доступную историю Git на случайно добавленные секреты. Публичность репозитория сама по себе не подтверждает, что такой аудит проведён.
5. После изменения документов проверять ссылки и Markdown, затем открывать PR; документационные правки сами по себе не должны запускать production-деплой.

## Ограничения

Инвентаризация пути/размера охватила Markdown-файлы в дереве, но не каждый из 220 документов прошёл построчную экспертную вычитку. Проценты языка для всего набора не заявляются. Перед применением технических инструкций сверяйте их с кодом и CI на текущем коммите.
