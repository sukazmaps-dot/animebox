# Исправление геометрии и восстановления постеров AnimeBox

## 1. Задача и границы патча

Исправить видимые тёмные полосы и неодинаковые размеры постеров в недельном
расписании. Устранить потерю единственной попытки восстановления изображения,
когда медиа-домен временно исключён общим circuit breaker.

Это две независимые неисправности: корректная CSS-геометрия не восстанавливает
недоступный исходный файл, а исправление сетевой цепочки не исправляет оболочку.
Работа охватывает `/schedule` и общий `AnimeImage`, используемый также на главной.
Настройки DNS, секреты, таблицы и Worker в этом патче не меняются.

## 2. Наблюдения и степень подтверждения

- На приложенных скриншотах часть изображений заменена локальным логотипом.
  Это состояние fallback, а не доказательство отсутствия постера в базе.
- На увеличенном скриншоте справа от изображения видна прямоугольная тёмная
  полоса: класс фиксированного размера назначен внутреннему img, тогда как
  оболочка компонента занимает другую площадь.
- В коде общий media circuit открывается после четырёх разных неудачных
  источников в пределах восьми секунд и действует 60 секунд.
- Единственный retry ранее запускался через 20–45 секунд, то есть мог пройти
  внутри блокировки; окончания блокировки store самостоятельно не объявлял.
- Calendar использовал preset large и стандартный sizes для больших карточек.
- Проверенный публичный `/api/schedule` возвращает URL изображений, включая
  `Я перевоплотился в гоблина, вопросы есть?` из скриншота. Его большой постер
  через `/api/image?...&fallback=error` вернул HTTP 200 и image/jpeg при curl.
  Python-клиент на тех же маршрутах получил 403: результат зависит от клиента
  и сам по себе не доказывает постоянную недоступность постера у пользователей.

## 3. Геометрия календаря

1. Добавить необязательный `containerClassName` в AnimeImage. Существующий
   `className` сохранить для внутреннего img, чтобы не менять другие карточки.
2. В недельном календаре перенести `weekly-calendar__poster` на контейнер.
3. Фиксировать оболочку в 28 × 42 CSS px, пропорция 2:3, на всех breakpoint.
4. Зафиксировать первый столбец event-main в 28px; тексту оставить minmax(0,1fr).
5. Оболочка отвечает за border-radius, overflow и вертикальное центрирование.
   Img занимает 100% её ширины и высоты, object-fit cover, без второго размера.
6. Loading, loaded и fallback занимают одну площадь; текст и время не смещаются.
7. Проверить короткие и двухстрочные названия, fallback и постеры разной исходной
   пропорции. Никаких правых полос, растяжения оболочки или горизонтального overflow.
8. Сохранить компактные строки, существующие ссылки и Portal-подсказки.

## 4. Размеры сетевых вариантов

- Календарь использует sourcePreference compact, preset tiny, quality 60,
  sizes 28px. Браузер выбирает вариант с учётом DPR.
- Список допустимых размеров Worker не расширяется. Сжатие не выполняется в React.
- Нативная lazy-загрузка сохраняется; внеэкранные постеры не становятся eager.
- При прямом резервном запросе не передавать Referer: no-referrer, как уже делает
  AnimeImageCascade. Это не обход контроля доступа и не гарантия доступности origin.

## 5. Жизненный цикл общего circuit breaker

1. Сохранить текущие пороги и защиту от массовых запросов при недоступном media.
2. На каждый открытый origin ставить один общий таймер до blockedUntil.
3. По истечении очистить блокировку и счётчики и увеличить revision store,
   чтобы подписанные компоненты получили обновление.
4. Если системные часы изменились и срок ещё не истёк, перевыставить таймер.
5. При уходе последнего подписчика удалить таймеры. Сам срок блокировки сохранить;
   при новом подписчике заново обслуживать его окончание.
6. SSR сохраняет snapshot 0; браузерное состояние не писать в sessionStorage.
7. Успешно показанные картинки не переключать при ошибках соседних файлов.

## 6. Retry без потери попытки

1. По источникам конкретной картинки вычислять минимальное оставшееся время
   блокировки её известных media origins. Если хотя бы один доступен — ждать не нужно.
2. Первое восстановление планировать не раньше обычного jitter 20–45 секунд
   и не раньше открытия доступного media origin плюс jitter 1–6 секунд.
3. Непосредственно перед retry ещё раз проверить блокировку: она могла возникнуть
   позднее или на другом origin. Пока все media origins заблокированы,
   перевыставить таймер, не расходуя попытку.
4. Offline не расходует попытку; online планирует проверку с прежним jitter.
5. После разрешённой попытки счётчик увеличить один раз. Бесконечные retries,
   polling и постоянный cache-busting не вводить.
6. Смена набора URL сбрасывает счётчик для новой картинки. Unmount очищает таймер
   и обработчик online. Обычные revision store не перезапускают jitter постоянно.

## 7. Сценарии сетевых отказов

Проверять настоящие компоненты со стабилизированными ответами:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Media работает | Одна выбранная картинка, loaded, корректная оболочка |
| Media/браузерный источник не работают, proxy работает | Переход к proxy, loaded |
| Все кандидаты не работают | Локальная заглушка, без бесконечных запросов |
| Четыре разных media failures | Общая минутная блокировка сохраняется |
| Retry достиг блокировки | Попытка не расходуется до доступного media origin |
| Блокировка закончилась, origin восстановился | Постер заменяет заглушку |
| Один media origin заблокирован, другой доступен | Доступный origin не задерживается |
| Нет URL изображения | Стабильная заглушка, без сетевой попытки восстановления |
| Успешная картинка и ошибки соседей | Успешная картинка сохраняется |
| Уход со страницы / возвращение | Таймеры очищены / восстановлены по сроку |

## 8. Проверки и критерии приёмки

- TypeScript production build и все существующие prebuild-проверки.
- ESLint изменённых TS/TSX файлов.
- Unit-проверка общего circuit с управляемыми часами: порог, срок, уведомление,
  повторная подписка, очистка таймеров и несколько media origins.
- Browser-проверка календаря на 390, 1440, 1920px в светлой и тёмной теме;
  размеры оболочки и img совпадают с допуском 1px, пропорция 2:3.
- Browser-проверка реального AnimeImage: отказ, fallback, восстановление после
  cooldown и ограниченное число попыток. Время можно ускорять только в тесте.
- Существующие schedule-poster-cascade, Tooltip и page-consistency регрессии.
- Отдельно сообщить, какие проверки используют фиксированные upstream-ответы:
  они доказывают клиентское поведение, но не доступность всех production-постеров.

## 9. Публикация и наблюдение

Подготовить отдельный commit/PR с результатами проверок. Мерж и production-релиз
выполнять по разрешению пользователя. После публикации проверить проблемные
тайтлы в браузере пользователя и Network: currentSrc, HTTP status, Content-Type,
data-image-state и индекс кандидата. Не утверждать, что все отсутствующие постеры
исправлены, если исходный файл недоступен или URL отсутствует.

## 10. Откат

При регрессии откатить этот commit обычным revert. Изменений данных и миграций нет.
Существующие карточки совместимы: className продолжает назначаться внутреннему img.

## 11. Результат реализации и проверки

Реализованы оболочка 28 × 42, tiny/sizes/quality, no-referrer для резервных
источников, таймер окончания cooldown и retry без расходования попытки в блокировке.
Локальный логотип ограничен размерами оболочки.

Проверки 11 октября 2026:

- `npm run build`: все prebuild gates и production Next build прошли.
- Финальный `npx next build` после ограничения логотипа прошёл.
- ESLint трёх изменённых TS/TSX файлов: ошибок и предупреждений нет.
- `npm run schedule-media:check`: новая проверка cooldown и существующие проверки
  URL/SSRF/редиректов/расписания/каталога/manifest прошли.
- `schedule-poster-recovery-smoke.mjs`: шесть комбинаций 390/1440/1920 × dark/light,
  настоящие Calendar/AnimeImage, заглушка, восстановление после cooldown, размеры
  оболочки и картинки, tiny-вариант и отсутствие повторов после успеха.
- `schedule-poster-cascade-smoke.mjs`: четыре настоящих постера восстановились
  через резервный серверный источник.
