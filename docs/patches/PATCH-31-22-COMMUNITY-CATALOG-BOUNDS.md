# Patch 31.22 — ограничение памяти каталога и тайм-ауты Supabase

**Статус:** реализация в отдельной ветке; до принятия PR необходимы CI и ревью. Production-деплой не выполнялся.

## Цель

Продолжить Patch 31.19–31.21: убрать ещё один источник неограниченного числа удерживаемых Promise и фоновой работы в горячем пути каталога. Не считать этот участок единственной причиной прежних пиков RSS до ~2 ГБ без подтверждения production-метриками.

## Подтверждённые проблемы в коде main

1. `lib/community-server.ts` уже ограничивает кэш каталога 2 000 строками, но `animeCatalogReadInFlight` не имел лимита числа разных незавершённых batch-запросов.
2. Чтение `anime_catalog` для cache miss не имело явного `abortSignal` deadline. При задержках Supabase уникальные batch-ключи могли оставаться в карте до завершения операции.
3. `animeCatalogRefreshInFlight` дедуплицирует одинаковые ID, но не ограничивал суммарное количество параллельных обновлений разных тайтлов. Обновление включало lease RPC, чтение внешнего каталога и upsert без явного тайм-аута именно на DB-запросах.
4. `tryAcquireRuntimeRefreshLease` / `releaseRuntimeRefreshLease` не задавали deadline для RPC. Ошибки lease уже обрабатывались fail-open/fail-safe; теперь задержка RPC ограничена по времени.

Эти пункты доказывают отсутствие некоторых защитных лимитов, но не доказывают, что указанные карты действительно вызвали максимальное потребление памяти в Railway.

## Объём изменений

### 1. Ограничить незавершённые чтения каталога

- Не более **32** уникальных запросов в `animeCatalogReadInFlight` на один процесс.
- Идентичные batch-запросы присоединяются к существующему Promise до проверки лимита.
- Если достигнут предел, новый уникальный запрос получает управляемую ошибку HTTP 503 через существующий `ApiError`; он не запускает скрытый обходной DB-запрос и не становится ложным cache miss/404.
- Чтение `anime_catalog` получает `AbortSignal.timeout(1800)`.
- Существующий cache TTL 60 секунд, limit 2 000, ключи, данные и правила fresh/stale остаются без изменений.

### 2. Ограничить обновление метаданных

- Не более **4 активных** обновлений и **16 ожидающих** на один процесс.
- Всего не более **20** уникальных ID в `animeCatalogRefreshInFlight`; повторный запрос того же ID получает существующий Promise.
- Ожидание свободного слота ограничено **8 секундами**.
- При перегрузке для существующего тайтла допускается вернуть ранее проверенную строку каталога; для тайтла без проверенной строки возвращается управляемый 503, а не поддельный 404.
- Upsert метаданных получает timeout **1800 мс**. Ошибки/тайм-ауты не превращаются в успешно закэшированную новую запись.
- Очистка `animeCatalogRefreshInFlight` остаётся в `finally`, включая ошибки/отмены/тайм-аут очереди.
- Политика обновления устаревшей метаинформации, схема ответа и формат данных не меняются.

### 3. Ограничить RPC координации

- RPC получения и освобождения runtime-refresh lease ограничены тайм-аутом **1200 мс**.
- Координация остаётся оптимизацией отказоустойчивости: acquisition сохраняет существующий fail-open и локальную дедупликацию, release не ломает пользовательский запрос при неудачной очистке.
- TTL lease, scope, ключи, SQL-функции и схема Supabase не меняются.

### 4. Регрессионные тесты

Новый `tests/community-catalog-memory-bounds.cjs` использует мокнутый Supabase и фикстуры, не делает production-запросов и не изменяет пользовательские данные. Он проверяет:

- 32 удерживаемых уникальных чтения допускаются, 33-е отклоняется, лимит не обходится дополнительным запросом;
- в сценарии 21 уникального обновления одновременно активны максимум 4; допускается максимум 16 ожидающих, дополнительный ID возвращает 503;
- все принятые обновления завершаются и удаляются из in-flight структуры после завершения;
- deadline чтения, записи и обоих lease RPC присутствует в коде.
- Тест включён в существующий `npm run railway-cost:check`, который уже запускается в AnimeBox Quality Gate.

## Критерии приёмки

1. `node tests/community-catalog-memory-bounds.cjs` проходит без сетевых вызовов.
2. `npm run railway-cost:check` проходит целиком.
3. TypeScript, целевой ESLint и production build проходят в CI на точном head SHA.
4. Существующие сценарии: сохранение избранного (до 12 тайтлов Premium), добавление в библиотеку, старт просмотра, рейтинги и комментарии работают; перегрузка возвращает 503 вместо зависания/ложного 404.
5. При нормальной нагрузке запросы не начинают массово получать 503; лимиты срабатывают только при фактическом насыщении.
6. После деплоя сравнить RSS, `heapUsed`, `external`, `arrayBuffers`, latency, 5xx и OOM на сопоставимых временных окнах. Синтетический тест подтверждает ограничение задач, но не измеряет экономию production RAM.

## Что не входит в патч

- Нет изменений миграций SQL, данных или RLS.
- Нет новых зависимостей, Redis, сервисов, регионов, реплик или настроек лимитов Railway.
- Не изменяются player, Premium, платежи, Watch Together, публичный API-контракт успешных ответов, CDN или Cloudflare Worker.
- Нет автоматического merge/deploy.
- Не заявляется достижение целевого RSS 100–200 МБ до получения реальных измерений.
