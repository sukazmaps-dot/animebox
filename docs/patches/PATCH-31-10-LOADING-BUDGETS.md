# Patch 31.10 — ограничение ожидания и объединение публичных загрузок

## 1. Задача и основание

17 октября 2026, около 16:45–16:49 по Казахстану, production Railway зарегистрировал ответы страниц тайтлов до 57 секунд, API до 58 секунд и image proxy до 42 секунд. На одном запросе Telegram register зафиксировано 80 секунд. Часть клиентов отменяет ожидание (499). Статические CSS/JS в той же выборке отвечают за 2–7 мс. За два часа 5634 HTTP-запроса, пиковые двухминутные корзины около 595 запросов. Это не число людей и не доказательство источника Reddit.

Сервис Online, память в момент проверки около 0.29 ГБ при лимите 1 ГБ; максимум за час около 0.72 ГБ. CPU не достигает лимита. Обнаружены таймауты сохранённых метаданных и Shikimori; причина всех задержек окончательно не локализована. Измерения curl из среды агента включают около 6 секунд TLS и не подходят как оценка скорости для пользователей Казахстана.

Код подтверждает два неограниченных ожидания: три запроса readLocalLocalization без abortSignal и RPC rate limiter перед API, включая каждую картинку. fetchWithRetry без переданного signal также не имеет общего таймаута; TimeoutError раньше мог повторяться. Эти пути исправляются в первом срочном патче.

## 2. Границы

Входит: бюджеты сетевого ожидания, сохранение fail-closed защиты API, объединение конкурентных публичных загрузок, небольшой кеш локализации и изображений, выдача предыдущего успешного AniList результата при сетевой ошибке, освобождение HTTP response streams при повторах/редиректах, регрессионные тесты.

Отдельно: переработка редактора, новая архитектура рекомендаций, изменения личного кабинета, миграции, изменение CDN/DNS/секретов, масштабирование и перенос сервисов. Данный патч не обещает полную загрузку любой страницы за 1 секунду: есть другие серверные зависимости и сети пользователя.

## 3. Контракты реализации

### 3.1 fetchWithRetry

- Для вызова без signal создать один AbortSignal.timeout(8000) на всю цепочку, а не новый на каждую попытку.
- Переданный signal сохранить: короткие сроки и отмена клиента имеют приоритет; более длинные явно заданные бюджеты также сохраняются.
- Проверять signal до попытки, не повторять AbortError/TimeoutError/отменённый signal.
- Backoff должен прерываться тем же signal, очищать timer/listener после завершения.
- Перед повтором освобождать body предыдущего временного HTTP-ответа.
- Существующий upstream concurrency shield, max attempts, retry для 429/5xx остаются.
- Бюджет распространяется на HTTP body посредством того же signal fetch; API возвращает Response, поэтому вызывающая сторона должна читать body как прежде.

### 3.2 Локализация тайтла

- Три публичных чтения (anime_search_documents, anime_catalog, anime_availability) выполняются параллельно с общим signal 1500 мс.
- Между посетителями одинаковый anime ID использует один in-flight Promise.
- Успешный полный набор результатов хранится 60 секунд, максимум 1000 ключей.
- Ошибочный/частичный набор не сохраняется в успешном кеше; текущий запрос может использовать доступные поля как раньше.
- Русское описание, сохранённое описание, MAL mapping и приоритеты данных не изменяются.
- Кеш не содержит пользовательские данные, cookies, токены и настройки профиля.

### 3.3 AniList detail

- Поверх существующего Next unstable_cache добавить process-local single-flight по числовому ID.
- Успешный AniList result хранится 30 минут, максимум 1000 ключей.
- При исключении загрузки допускается предыдущий успешный result ещё 6 часов после TTL. Это явно ограниченный stale-if-error, не вечное хранение.
- null не кешировать. Ошибку без предыдущего результата передавать существующему fallback локального/SEO каталога.
- React cache metadata/page, канонические slugs, providerSeason и фильтрацию допустимых тайтлов сохранить.
- Process cache не является распределённым и очищается после рестарта. Устойчивый Next cache сохраняет прежнее поведение; миграция хранилища не входит в патч.

### 3.4 Rate limiter

- RPC consume_api_rate_bucket ограничить 1500 мс через abortSignal.
- Не заменять durable guard локальным счётчиком и не разрешать запрос при отказе базы.
- true продолжает разрешать запрос; false возвращает 429; ошибка/таймаут возвращает существующий 503 no-store.
- Лимиты scopes, ключи/HMAC, IP trust, авторизация и RLS остаются прежними.
- При сбое БД часть запросов быстро вернёт 503: это предпочтительнее обхода защиты, но требует контроля error rate после выпуска.

### 3.5 Image proxy

- Проверка IP-лимита остаётся перед выдачей картинки, в том числе из process cache.
- Одинаковые одновременные URL объединяются до чтения всего body; нельзя отдавать один общий потребляемый Response нескольким клиентам.
- Кешировать только успешно проверенные bytes, content-type, максимум 1 МиБ на картинку, 32 ключа, TTL 60 секунд. Большие изображения до прежних 10 МиБ продолжают работать без сохранения в этом кеше.
- Проверки URL/redirect allowlist, credentials/port, MIME, размера, strict fallback=error и browser/CDN headers сохранить.
- Ошибку/placeholder не сохранять в новом положительном кеше.
- Освобождать body редиректов и ответов, которые не будут прочитаны.
- Уже существующий общий timeout fetchImage 8000 мс сохраняется: не добавлять новый timeout на каждый redirect.
- Сумма rate guard + image fetch имеет отдельные последовательные бюджеты; не называть её общим 8-секундным бюджетом всего endpoint.

## 5. Проверки приёмки

1. 20 конкурентных загрузок одного публичного ключа вызывают loader один раз.
2. Независимые ключи не смешиваются; null/error не становятся положительным кешем.
3. Просроченный успешный result возвращается при ошибке только внутри stale window, после него ошибка видна.
4. Отмена до fetch не создаёт запрос; отмена во время backoff не создаёт следующую попытку.
5. TimeoutError не запускает дополнительные retries; временный HTTP 503 может повторяться до max attempts в общем бюджете.
6. Полная локализация кешируется; частичная ошибка не закрепляется, следующий вызов повторяет чтение.
7. Rate limiter true/false/error сохраняет прежнее поведение; используется abortSignal, таймаут не fail-open.
8. Image proxy: успешные конкурентные клиенты получают полный body, origin вызывается один раз, strict fallback и allowlist неизменны.
9. Полный prebuild, TypeScript, целевой ESLint и production build проходят.
10. После разрешённого слияния/деплоя: проверить точный commit SHA Railway, Online, HTTP routes, error rate, p95 и логи за новый интервал. Сравнивать с production baseline по тем же маршрутам, отдельно от TLS агента.

## 6. Риски и откат

- Кеш локализации задерживает видимость правок каталога максимум на 60 секунд; личные данные не кешируются.
- Stale AniList может временно показывать предыдущие числа эпизодов/оценки, только при ошибке провайдера и ограниченное время.
- Короткий срок RPC может увеличить 503 при деградации БД. Мониторить отдельно, не отключать защиту для красивой статистики.
- Много уникальных URL не выигрывает от single-flight; размеры кешей ограничены.
- Отмена зависит от сетевого клиента, поддерживающего AbortSignal; тестировать с используемой версией Supabase.
- Откат: revert коммита патча, обычный deploy main. Изменений БД и env нет.

## 7. Результаты

Локально PASS: полный npm run prebuild (включая новый loading-budgets:check), TypeScript, целевой ESLint без ошибок/предупреждений, production Next build. Для build пришлось пересоздать только временный кеш Turbopack после ошибки его локальной persistence database; исходники и данные приложения не затрагивались.

Новые исполняемые тесты подтверждают: 20 ожидающих получают один результат/один loader; все ожидающие получают stale при ошибке; stale истекает; null и исключения не кешируются как успех; timeout и отмена backoff не создают новую попытку; stream ответа 503 освобождается; retry 503→200 работает. Rate limiter сохраняет true/429/503 и no-store. Установленный Supabase SDK с контролируемым fetch действительно передаёт AbortSignal и возвращает ошибку по его отмене. Это интеграция SDK, не измерение latency production DB.

Локализация: 20 конкурентных вызовов дают 3 чтения вместо 60, общий signal, частичный сбой повторяется на следующем запросе. Image proxy: 20 клиентов получают полные bytes при одном origin fetch; 20 вызовов защиты сохраняются; ошибки и изображения >1 МиБ не занимают положительный кеш. Старые tests/media-schedule-fix.cjs, tests/tooltip-poster-reliability.cjs и tests/anime-detail-persisted-metadata.cjs проходят с обновлёнными fixtures для кеша и abortSignal.

Browser smoke: 18 сценариев реальной разметки при 360/390/430/740/844/960/1100/1440/1920px и zoom аватара 1/3. На ширинах от 740 проверяется pointer hit на раскрытом меню над навигацией. Фикс меню не меняет TSX плеера и его iframe lifecycle. Физические устройства и реальный production before/after после этого патча ещё не проверены. Не заявляем измеренное ускорение production до деплоя.

## 8. Дополнение: меню озвучки (скриншот пользователя)

Раскрытый список озвучек перекрывается следующими sibling cards (серии и библиотека). Локальный z-index панели не поднимает ancestor stacking context. В существующем владельце геометрии EpisodePageDensity.module.css при aria-expanded=true поднимаются player root и header, затем текущий dropdown. Закрытое состояние не повышает слой; fullscreen iframe не перемонтируется, layout/отступы страницы не меняются. Новых !important нет. Browser smoke дополнен проверкой elementFromPoint в области пересечения меню и реального EpisodeQuickSelector на 740–1920px; базовый набор 360–1100 сохраняется, добавлены 1440/1920.
