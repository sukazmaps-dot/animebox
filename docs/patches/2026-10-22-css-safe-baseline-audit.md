## 1. Цель патча

Зафиксировать исходное состояние CSS перед будущей нормализацией названий файлов и постепенным улучшением архитектуры стилей. Этот патч не должен менять поведение AnimeBox: он документирует текущие цифры, имеющиеся проверки, ограничения и критерии безопасного продолжения.

Принцип: **сначала измеряем и фиксируем baseline, затем меняем небольшие группы файлов по одной**. Никакая косметическая чистка не важнее работающего интерфейса.

## 3. Что входит в этот патч

1. Добавить этот документ с базовыми цифрами, границами и процедурами проверки.
2. Сохранить ссылки на действующие автоматизированные проверки CSS.
3. Зафиксировать, что следующий этап с именами файлов не должен одновременно менять CSS-правила, селекторы, значения, порядок каскада или JSX.
4. Использовать Draft PR, чтобы GitHub Actions проверил изменение до любого слияния.

## 4. Что строго не меняем

- Ни один существующий CSS-файл и его имя.
- `app/layout.tsx` и порядок CSS-импортов.
- Селекторы, объявления, custom properties, media queries и `!important`.
- React/TypeScript-компоненты, маршруты, API, данные, авторизацию, Supabase, Telegram и настройки деплоя.
- `package.json`, lock-файл и зависимости.
- Production-деплой и настройки окружений.

В этом патче ожидается ровно один изменённый файл: этот Markdown-документ. Если появятся дополнительные изменения приложения, их нужно вынести в отдельный патч.

## 5. Проверки baseline

В репозитории уже объявлены следующие команды:

```bash
npm run css:inventory:check
npm run css-cascade:check
npm run visual:check
npm run mobile-shell:check
npm run css-route-scope:check
npm run frontend-architecture:check
npx tsc --noEmit
npm run build
```

Основная команда `npm run build` использует lifecycle `prebuild`; в текущем `package.json` он содержит большой release quality gate. Поэтому полный build может быть существенно тяжелее отдельных CSS-проверок.

В GitHub Actions workflow `.github/workflows/animebox-quality.yml` запускается для Pull Request в `main`. В нём предусмотрены `npm ci`, CSS inventory/regression-проверки, проверки владения стилями и дополнительные проектные проверки. Для acceptance этого патча нужен успешный CI на head-коммите PR. Успех старого baseline CI не заменяет проверку нового PR.

## 6. Гипотезы для последующих этапов — пока не исправлять

- Названия с номером патча усложняют понимание назначения стилей, но само по себе имя не доказывает, что файл можно переименовать или удалить.
- Повторяющиеся глобальные селекторы и `!important` требуют анализа контекста и порядка каскада; автоматическая массовая чистка опасна.
- Статические отчёты о неиспользуемых стилях нужно сверять с импортами маршрутных layout, динамическими подключениями и реальным отображением.
- Известная устаревшая ссылка на `components/ScrollRow.module.css` в `components/ScrollRow.tsx` отмечена в CSS-инвентаризаторе как legacy reference. Её исправление или удаление не относится к документационному патчу; сначала нужно проверить реальные usages и активную реализацию `components/ui/ScrollRow.tsx`.

## 10. Первый статический проход: карта подключений (2026-10-22)

Проверена текущая `main` на baseline commit `df2b9a134c5fda7a0e47d5b71694c47ec20f7e2c`; это чтение исходников GitHub, а не локальный запуск приложения.

### Подтверждено

- В `app/layout.tsx` найдено 74 CSS-импорта.
- Каждый из 74 относительных CSS-путей, объявленных в корневом layout, разрешается в существующий файл. На этом уровне не найдено отсутствующих файлов импорта.
- В дереве репозитория остаются 218 CSS-файлов: 98 CSS Modules и 120 глобальных CSS.
- 61 CSS-файл содержит `patch` в имени.
- Среди CSS-файлов непосредственно в каталоге `app/` есть 43 глобальных файла, которые не импортируются напрямую из `app/layout.tsx`. **Это список для проверки, не список неиспользуемых файлов.**
- Подтверждены маршрутные импорты вне корневого layout: `app/anime/[slug]/layout.tsx` подключает 8 CSS-файлов, а `app/premium/layout.tsx` — 7. Поэтому поиск только по `app/layout.tsx` не может определить неиспользуемые стили.

### Предварительные выводы

1. Не следует объединять все глобальные CSS-файлы в один файл: часть стилей намеренно ограничена маршрутом, а порядок импортов может определять каскад.
2. Следующий этап должен построить карту импортов по всем `layout.tsx`, `page.tsx`, компонентам и скриптам/тестам, прежде чем помечать CSS как кандидата на удаление.
3. Отдельно требуется проверить дублирующиеся селекторы и переопределения, особенно `!important`, с учётом порядка загрузки и media queries.
4. Переименование файлов и чистка неиспользуемых правил — разные задачи; их не смешивать в одном diff.

### Границы этого прохода

- Это статическая проверка структуры и путей, не визуальная проверка браузера.
- Факт существования импорта не гарантирует, что все правила файла нужны; отсутствие импорта из корневого layout не доказывает, что файл мёртвый.
- CSS не менялся, production не затрагивался, сборка и браузерные проверки этим проходом не запускались.

### Следующий шаг

Составить полный граф CSS-импортов и связать его с существующими проверками `css:inventory:check`, `css-cascade:check` и маршрутными проверками. Только после этого сформировать три списка: подтверждённо используемые файлы, файлы с неясным владельцем и безопасные кандидаты на удаление/объединение.
