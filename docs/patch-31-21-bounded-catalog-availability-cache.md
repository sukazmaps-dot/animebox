# Patch 31.21 — ограничить кэш проверок доступности каталога

## Причина

В `lib/source-availability.ts` серверный `catalogAvailabilityCache` имел TTL для каждой записи, но не удалял протухшие записи глобально и не ограничивал количество уникальных ключей. При обходе множества разных страниц тайтлов старые ключи могли удерживаться в `Map` до перезапуска процесса.

В `app/api/player/direct-source/route.ts` была вторая ошибка: очистка карты rate-limit выполнялась только после увеличения счётчика уже известного IP. Для нового IP функция сохраняла bucket и сразу возвращалась, поэтому cleanup не срабатывал на потоке уникальных адресов. Карта могла расти без ограничения.

Оба дефекта подтверждены кодом и могут удерживать память в живом Node.js-процессе. Пока нельзя утверждать, что только они объясняют весь RSS около 2 ГБ.

## Изменение

- Ограничить число записей 2 000 на экземпляр процесса.
- Раз в 30 секунд удалять записи с истёкшим TTL, даже если их ключи больше не запрашиваются.
- Использовать порядок `Map` как простую LRU-политику: cache hit обновляет давность записи, при превышении лимита вытесняется самая старая.
- Начинать TTL после завершения проверки, а не до ожидания внешнего провайдера.
- Ограничить карту IP-бакетов `/api/player/direct-source` 2 000 записями и очищать истёкшие buckets периодическим sweep не чаще раза в 30 секунд.
- При заполненной карте отклонять новые уникальные IP с `429` за O(1) до следующей регулярной очистки; не запускать полный обход карты на каждом запросе. Старые IP-бюджеты и окна в 60 секунд сохраняются.
- Не менять внешнюю семантику `available / unavailable / unknown`, TTL 90 секунд для `unknown` и 6 часов для подтверждённого ответа, формат API или данные пользователей.
- Не добавлять Redis, сервисы, миграции или новые production endpoint'ы.

## Проверка

`tests/source-availability-cache-bounds.cjs` запускает модуль с локальными моками провайдеров. Тест заполняет кэш уникальными тайтлами, проверяет cache hit, вытеснение старейшей записи и истечение TTL.

`tests/direct-source-rate-limit-memory-bounds.cjs` прогоняет route handler с моками: 2 000 уникальных IP проходят к замоканному провайдеру, следующий уникальный IP отклоняется, лимит одного IP сохраняется, а по истечении окна ёмкость освобождается. Реальные HTTP/Supabase-запросы тесты не делают.

Оба теста включены в `npm run railway-cost:check`, поэтому попадают в Quality Gate.

## Критерии приёмки

1. Размер завершённого кэша не превышает 2 000 записей.
2. Протухшие записи очищаются периодически, не только при повторном обращении к тому же тайтлу.
3. Свежие cache hit и действующая логика доступности источников сохраняются.
4. TypeScript, targeted lint, целевые регрессии и production build проходят.
5. После деплоя сравнить RAM и динамику роста на сопоставимом трафике. Не объявлять конкретную экономию памяти без измерений.
