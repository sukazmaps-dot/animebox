# Патч 1: надёжность AnimeBox после переноса на Railway

Статус: техническое задание и критерии приёмки. Ветка: `patch/reliability-foundation`.

## 1. Проблема и результат

После смены хостинга сайт может успешно собираться, но отдельные функции перестают работать из-за окружения, Origin, неверного webhook или внешнего API. Сейчас существуют подробные панели мониторинга, но нет короткой проверки базовой конфигурации перед переключением Railway на новый процесс. Пользователь сообщил о молчащем Telegram-боте; причина пока не подтверждена журналами Telegram.

Результат патча: каждый положительный статус сопровождается точным описанием пройденной проверки. Отдельно показываются конфигурация, доступность зависимости и границы проверки. Владелец получает безопасный способ проверить и восстановить webhook без передачи ключей в браузер или чат.

## 2. Границы

Работы включают проверку окружения, endpoints здоровья, экран диагностики, восстановление Telegram, smoke-проверку выпуска, CI и инструкцию отката. Существующий мониторинг источников, инцидентов, фоновых задач и БД сохраняется и используется через страницу `/admin/health`.

Этот патч не меняет дизайн пользовательских страниц, схему БД, модель аккаунтов, платежи, алгоритмы рекомендаций или воспроизведение видео. Реальная авторизация Google/Telegram и доставка команды `/start` требуют отдельных пользовательских проверок; публичная smoke-проверка их не имитирует и не объявляет выполненными.

## 3. Проверка конфигурации

Реализовать чистую функцию, принимающую словарь окружения и возвращающую список фиксированных кодов, уровень `error`/`warning`, название сервиса и рекомендацию. Значения переменных, JWT, URL с ключами, токены и секреты не возвращаются.

Блокирующие условия:

- Отсутствует или некорректен `NEXT_PUBLIC_SUPABASE_URL`: допустим HTTPS без логина, пароля, query и fragment.
- Отсутствует публичный ключ Supabase либо вместо него указан секретный ключ/service_role JWT.
- Отсутствует серверный `SUPABASE_SERVICE_ROLE_KEY` либо его формат очевидно не соответствует секретному ключу/service_role JWT.
- Опубликована переменная `NEXT_PUBLIC_` с известным именем серверного секрета.
- Заданный `NEXT_PUBLIC_SITE_URL` противоречит каноническому домену production.

Предупреждения для отдельных функций:

- Google Client ID отсутствует или не заканчивается на `.apps.googleusercontent.com`.
- Telegram Client ID отсутствует или не является положительным безопасным целым числом.
- Telegram Client Secret, Bot Token или Webhook Secret отсутствует; Webhook Secret содержит недопустимые символы.
- Числовая часть Bot Token не совпадает с Telegram Client ID.
- Не настроены `KODIK_TOKEN`, `CRON_SECRET` или `ADMIN_OWNER_IDS`.

Наличие переменной подтверждает только конфигурацию. Валидность ключа подтверждается отдельным запросом к сервису. Функция не изменяет окружение и не выводит его значения даже при ошибке.

## 4. Здоровье процесса и готовность Railway

`GET /api/health` возвращает минимальный JSON: процесс отвечает, идентификатор версии патча и SHA выпуска, если платформа его передала. Никаких названий проблемных переменных в публичном ответе.

`GET /api/health/ready` возвращает HTTP 200 при корректной базовой конфигурации и 503 при блокирующих ошибках. Предупреждения Google/Telegram не отключают весь сайт. Обе проверки динамические, без CDN-кеширования и без внешних запросов.

Railway использует `/api/health/ready` как healthcheck нового deployment. В `railway.json` задать путь и таймаут. Это проверка запуска перед переключением трафика, а не непрерывный мониторинг production.

Proxy допускает обход проверки канонического Host и edge-secret **только для GET/HEAD двух точных путей здоровья**. POST, соседние пути, административные API и webhook сохраняют существующую защиту. Запуск без production-ключей на этапе сборки допустим; runtime готовность определяется фактическим окружением.

Node instrumentation при запуске пишет только фиксированные коды проблем и безопасный идентификатор выпуска. Отсутствующий необязательный ключ не вызывает исключение при сборке. Никакого `console.log(process.env)`.

## 5. Закрытая диагностика

`GET /api/admin/reliability` доступен owner/admin через существующие проверки аккаунта, ролей и лимитов. Ответ всегда `private, no-store`. Модератор и анонимный пользователь не получают диагностические данные.

Экран на `/admin/health` запускает диагностику по кнопке. Список проблем конфигурации и результаты сетевых проверок отображаются отдельно. Не допускается бесконечный автоматический опрос или незаметное восстановление webhook.

Сетевые проверки выполняются независимо и параллельно с ограниченным временем и размером ответа:

| Проверка | Что подтверждает | Что не подтверждает |
| --- | --- | --- |
| Supabase Auth settings | Auth API принимает публичный ключ | Успешный вход конкретного пользователя |
| Supabase REST monitoring table | Серверный ключ и существующая таблица доступны | Все миграции и все SQL-запросы исправны |
| Kodik API | Поиск известного аниме возвращает источник | Видео действительно воспроизводится на устройстве |
| Telegram getWebhookInfo | Telegram отвечает, URL/типы обновлений/очередь известны | Реальную доставку и ответ на `/start` |

Для каждого результата: сервис, фиксированный код, состояние, время проверки и короткое действие. Ответы внешних API и тексты произвольных исключений не передавать клиенту. При таймауте одного сервиса остальные результаты сохраняются. URL запросов определяются кодом/доверенным серверным окружением; пользователь не задаёт произвольный адрес.

Зелёный Telegram-результат означает только корректные известные настройки; свежая ошибка доставки или ожидающая очередь показываются как требующие внимания. Историческая ошибка без очереди не является доказательством текущего отказа.

## 6. Диагностика и восстановление Telegram

Использовать относящуюся к Telegram реализацию из невыпущенного PR №179, без переноса других изменений каталога.

`GET /api/admin/telegram-webhook`: owner/admin, сервер вызывает getWebhookInfo. Показать наличие токена и секрета, формат секрета, текущий/ожидаемый URL, очередь, типы обновлений и последнюю ошибку доставки. Удалить секреты, credentials, query и fragment из отображаемых URL. Тексты Telegram должны проходить редактирование секретов.

`POST /api/admin/telegram-webhook`: только owner, существующая защита браузерных mutations и JSON body до 1024 байт. Допустимо только `{ "action": "repair" }`.

Порядок восстановления:

1. Проверить наличие и формат секретов.
2. Через getMe проверить, что токен относится к ожидаемому боту YourAnimeBoxBot. Несовпадение запрещает изменение webhook.
3. Получить текущие настройки getWebhookInfo.
4. Отправить пустое `{}` в канонический webhook с серверным secret header. Требовать HTTP 200 и `{ok:true}`. Redirect, 401, 403, 5xx и неправильный JSON прекращают операцию.
5. Вызвать setWebhook с фиксированным `https://youranimebox.com/api/telegram/webhook`, серверным секретом и `drop_pending_updates:false`.
6. Сохранить существующий список allowed_updates, добавив message/pre_checkout_query/subscription. Пустой список остаётся пустым, сохраняя стандартное поведение Telegram.
7. Повторить getWebhookInfo и проверить URL и типы обновлений.
8. Зафиксировать попытку и результат в существующем admin_audit_log. Если аудит попытки недоступен, не менять webhook. Если запись результата не удалась после изменения, вернуть правдивый результат с предупреждением, а не ложное «восстановление не выполнено».

Не вызывать sendMessage, не создавать платежей и не очищать очередь. После восстановления возможна доставка ранее ожидавших команд; экран сообщает об этом. Секрет, установленный у Telegram, нельзя прочитать обратно: успешный setWebhook и повторная проверка не заменяют реальный тест доставки.

## 7. Smoke-проверка выпуска

Добавить `scripts/release-smoke.mjs`, доступный через npm. Без учётных данных проверить:

- HTTP/JSON и schema минимальной готовности;
- соответствие SHA ожидаемой версии, если он передан;
- главную страницу: HTTP 200 и HTML;
- публичную конфигурацию Google/Telegram: корректные public Client IDs;
- поиск Naruto: HTTP 200, массив результатов и хотя бы один результат.

Запросы ограничены таймаутом, redirects запрещены, ошибка превращается в фиксированный код и ненулевой exit code. Ни полный HTML, ни Client IDs, ни cookies не печатать. Скрипт поддерживает ожидание появления конкретного SHA с общим пределом времени, чтобы не принять старый deployment за новый.

CI запускает тесты патча на PR. Отдельный smoke workflow запускается после успешного Quality Gate main, вручную и периодически; после main должен дождаться именно SHA проверенного выпуска. Плановый запуск проверяет текущую доступность. Отсутствие SHA/нового deployment к сроку — ошибка, не зелёный результат.

## 8. Проверки и приёмка

| Сценарий | Ожидаемый результат |
| --- | --- |
| Корректные ключи | ready 200; функции перечислены отдельно |
| Нет серверного ключа | ready 503; публичный ответ без подробностей |
| service_role в публичном ключе | блокирующая ошибка, значения скрыты |
| Секрет с NEXT_PUBLIC_ | блокирующая ошибка |
| Нет Google/TG | предупреждение, сайт продолжает запускаться |
| Host healthcheck.railway.app, GET health | проходит до route |
| Тот же Host, POST health/admin/webhook | origin lock остаётся |
| Supabase timeout, Telegram отвечает | отказ Supabase не скрывает Telegram |
| Неправильный бот | setWebhook не вызывается |
| Webhook preflight 401 | setWebhook не вызывается |
| Pending updates > 0 | сохраняются; интерфейс не объявляет доставку проверенной |
| Админ пытается repair | 403 до внешнего запроса |
| Аудит недоступен | webhook не изменяется |
| Запись результата аудита упала | результат изменения сохранён, warning |
| Старый release SHA / пустой поиск | smoke завершится ошибкой |

Обязательны тесты отказов и безопасности, TypeScript, lint изменённых файлов, существующие gates и production build. Тесты используют подменённые внешние ответы, не production-токены. Production-проверка отдельно фиксирует фактически пройденные сценарии.

## 9. Выпуск и откат

Перед выпуском сохранить рабочий Railway deployment и проверить, что переменные заданы в нужном service/environment. Сборка не требует новых таблиц или миграций. Выпустить commit, дождаться readiness и smoke именно этой версии. Для бота владелец открывает `/admin/telegram`, проверяет данные, при необходимости восстанавливает webhook и отправляет `/start`, «❓ Помощь», «🔔 Уведомления» со своего аккаунта.

Переменные NEXT_PUBLIC Supabase должны быть доступны во время сборки, поскольку браузер использует встроенные в bundle значения. После их изменения нужна пересборка; readiness проверяет серверное окружение и не доказывает совпадение уже загруженного браузером старого bundle. Проверка реального входа остаётся обязательной.

Если новая версия ломает основные маршруты: выбрать предыдущий успешный deployment в Railway и выполнить rollback; затем повторить smoke на его SHA. Откат кода не откатывает изменённые environment variables и настройки Telegram. Если изменялся webhook, восстановить рабочий URL/секрет отдельно, сохраняя pending updates. При проблеме только одного провайдера не выполнять массовый откат без проверки базовых маршрутов.

## 10. Определение завершения

Завершено в коде: ТЗ сохранено, endpoints/диагностика/repair/workflows реализованы, тесты и сборка проходят, изменения подготовлены к выпуску. Завершено в production: новый SHA отвечает через канонический домен, smoke проходит; Telegram реально отвечает после восстановления и пользовательской команды. При отсутствии доступа к owner-сессии второй пункт по боту явно остаётся неподтверждённым.

## 11. Документация платформ

- Railway: [healthchecks](https://docs.railway.com/deployments/healthchecks), [config as code](https://docs.railway.com/config-as-code/reference), [Git commit variables](https://docs.railway.com/variables/reference). SHA автоматически доступен для deployment из GitHub; для другого источника отсутствие SHA не должно превращаться в подтверждение версии.
- Telegram: [getWebhookInfo и setWebhook](https://core.telegram.org/bots/api#setwebhook). Secret token не читается через getWebhookInfo; drop_pending_updates запрещён этим ТЗ.
- Next.js: [instrumentation](https://nextjs.org/docs/app/api-reference/file-conventions/instrumentation), [переменные окружения](https://nextjs.org/docs/app/guides/environment-variables).
