# AnimeBox: CPU и надёжность догрузки — техническое задание

## Цель и границы
Сократить повторную серверную работу без ухудшения персонализации, доступа к аккаунту, полноты расписания и точности учёта просмотра. Патч применим к Node на Railway и Vercel. Снижение wall-clock задержки не считать автоматически снижением active CPU: ожидание сети и работа процессора — разные метрики.

Патч состоит из проверенного исправления транспорта и ключей расписания (поставляется сейчас) и следующих оптимизаций, требующих измерений production. Не объявлять весь план завершённым после исправления одного таймаута. Не добавлять новые платные сервисы и cron без необходимости. Не менять DNS, секреты, схему базы и античит в этом пакете.

## Подтверждённая проблема догрузки
На Railway 05.10.2026 запрос /api/recommendations?limit=20&bucket=1&mood=any&intent=default&page=3 вернул HTTP 200 за 8.889202 секунды. Другие bucket этого же холодного набора: 6.241024, 3.675271, 6.523553 секунды. В клиенте таймаут был 7000 мс, максимум две попытки.

Следствие: сервер может успешно сформировать данные после прекращения ожидания клиентом. Повторный запрос не гарантирует отмену работы первого и увеличивает нагрузку. Это подтверждённый механизм ошибки «Не удалось загрузить ещё», но не доказательство, что все редкие ряды вызваны только им.

На скриншотах изображения уже видны. Отдельно проверять число кандидатов после персональных исключений и классификации по рядам. Не наполнять сезонный ряд несезонными тайтлами ради визуальной плотности. Ряд продолжений может законно содержать один доступный следующий сезон.

## Поставка 1: транспорт рекомендаций
1. Ожидание каждой попытки — 20 секунд, включая чтение JSON.
2. Таймаут имеет понятную ошибку и ручную кнопку повторения.
3. Не повторять автоматически запрос после клиентского таймаута: сервер мог продолжить расчёт.
4. Сохранить максимум две попытки для текущих HTTP 429/502/503/504; успешные ответы не повторять.
5. Сохранить общую карту запросов и независимую отмену ожидания потребителя: отмена одного ряда не должна отменять загрузку другого.
6. Сохранить валидацию ответа, cursor/page, append-only порядок, защиту от дублей и поколение запроса при смене настроения.
7. Не уменьшать пороги персонального совпадения и не менять ранжирование в транспортном исправлении.
8. Обновить regression guard, проверявший старый таймаут.

Приёмка: ответ на девятой секунде не вызывает старый семисекундный обрыв; неверный JSON не попадает в кэш; старое поколение не меняет текущую ленту; таймаут не порождает немедленную вторую серверную работу.

## Поставка 1: стабильные ключи расписания
1. Главная использует начало общего пятиминутного окна вместо уникального времени до секунды.
2. Границы главной: окно минус 6 часов, окно плюс 72 часа, limit=60.
3. Неявный серверный диапазон: общее окно минус сутки, плюс восемь суток.
4. Явно заданные from/to не округлять: пользовательские границы остаются точными.
5. Сохранить существующие публичные CDN-заголовки и upstream revalidate=300.
6. Объединять одновременные одинаковые AniList-запросы по from/to/page независимо от limit потребителя.
7. Ограничить карту выполняющихся запросов 64 ключами. При заполнении выполнять обычный запрос; не вытеснять обещание, ожидаемое другим потребителем.
8. Каждый потребитель получает отдельный Response.clone, чтобы чтение тела одним запросом не ломало другой.
9. Удалять запись карты и при успехе, и при исключении. Готовые тела здесь не хранить: их кэширует существующий Next fetch.
10. Сохранить fallback AniList → Shikimori → Jikan, сообщения об устаревших данных и реальные идентификаторы.

Ограничение: объединение работает внутри одного процесса/инстанса. На нескольких инстансах оно не является распределённой блокировкой. Уже существующие Next/CDN-кэши остаются отдельными уровнями. Округление общего окна меняет его максимум на 299 секунд, не время выхода события.

Приёмка: параллельные одинаковые запросы вызывают один upstream loader; разные страницы не смешиваются; тела читаются независимо; ошибка не отравляет следующий запрос; переполнение не растит карту.

## Поставка 1: уведомления
1. Не запускать второй fetch бейджа, пока первый выполняется.
2. Сохранить текущую частоту 30 секунд и немедленное обновление по событию при отсутствии активного запроса.
3. Сохранить pause в скрытой/offline вкладке.
4. Отменять запрос при размонтировании и смене пользователя; не применять ответ отменённого запроса к новому аккаунту.
5. Не использовать публичный кэш для персональных уведомлений.

## Следующая поставка: измерения и выбор горячих маршрутов
До изменения политик каталог/рекомендации/плеер собрать сопоставимые данные за 24–48 часов:
- запросы и вызовы функций по маршрутам;
- active CPU на 1000 запросов и на 1000 посещений;
- provisioned memory time, отдельно от active CPU;
- p50/p95 задержки и доля ошибок;
- cache hit/miss в CDN и серверных кэшах;
- доля фоновых вызовов после ответа;
- объём ответа и исходящий трафик;
- частота 429 внешних источников.

Не журналировать токены, cookies, email, названия поисковых запросов и полный URL с персональными параметрами. Использовать нормализованное имя маршрута, ограниченный набор категорий и выборку. Замер после патча должен иметь сопоставимую посещаемость и прогретость кэша. Не обещать процент экономии до сравнения.

## Следующая поставка: каталог и общие подборки
1. Проверить повторную фильтрацию availability при попадании в кэш главной: upstream-кэш не гарантирует отсутствия DB/CPU после его чтения.
2. Выделить общий публичный результат и персональные исключения. Никогда не помещать cookie/userId/профиль в публичный ключ.
3. Нормализовать page/limit/order/genre/season/year; ограничить число вариантов. Сортировать повторяющиеся query-параметры по контракту, не менять смысл фильтра.
4. Проверить пустые и degraded ответы: не хранить ошибку как успешный полный каталог на долгий срок.
5. Availability проверять пакетно, обновлять только устаревшие записи и ограничивать работу after(). after переносит работу после ответа, но не делает её бесплатной.
6. TTL подбирать по частоте изменения данных. Отдельная ручная инвалидизация для административного исправления.
7. Для Railway с несколькими репликами отдельно определить общий cache handler или принять независимые кэши; не вводить новый сервис до измерений.

## Следующая поставка: разреженные ряды
1. Зафиксировать исходный пул, количество после available, после hidden/watched, после taste и после назначения ряду.
2. Проверить сезон/year и реальные startDate, формат и MAL/AniList mapping.
3. Проверить сериализацию общих cursor между одновременно видимыми рядами: ограничение сканирования не должно ошибочно означать конец каталога.
4. Сохранить append-only порядок уже показанных карточек.
5. При валидном исчерпании узкого ряда скрыть стрелку дальнейшей догрузки или показать честное окончание, не выдавать сетевую ошибку.
6. При сетевой ошибке сохранить существующие карточки, курсор и ручной retry.
7. Предзагружать только следующий востребованный пакет. Не сканировать десятки страниц ради скрытого ряда.
8. Не смешивать продолжения, текущий сезон и случайные рекомендации для заполнения пустоты.

## Следующая поставка: фоновые запросы
1. Сначала измерить реальную частоту чата, присутствия, уведомлений и прогресса на активной/скрытой вкладке.
2. Для каждого запроса проверить visibility, online, overlap, очистку таймера и смену пользователя.
3. Объединять только семантически одинаковые запросы.
4. Межвкладочную координацию вводить отдельно, с takeover после закрытия вкладки и изоляцией аккаунта.
5. Не менять heartbeat плеера без тестов накопления доверенного времени, seek/pause/ускорения и доставки при выходе.
6. Не снижать realtime качество совместного просмотра ради экономии фонового polling сайта.

## Следующая поставка: ISR и боты
1. Определить публичную базу страницы аниме отдельно от личного прогресса/избранного.
2. Проверить cookies/headers динамических родителей до изменения revalidate.
3. Сохранить правильные 404, metadata/canonical и отсутствие утечки пользователя.
4. Регистрировать изменения публичных данных для адресной инвалидизации.
5. Проверить существующий shield и rate limit до добавления новых правил.
6. Ограничивать дорогие API по реальным всплескам, не блокировать поисковую индексацию без evidence.

## Установка и проверка после публикации
Пакет предназначен для той же рабочей копии AnimeBox, с которой готовились предыдущие исправления Cloudflare/catalog. Перед заменой сохранить локальные изменения. Пакет включает текущие версии затронутых файлов, включая ранее внесённые зависимости расписания; не накладывать вслепую на неизвестную другую ветку.

Распаковать в корень проекта с заменой. Выполнить npm run build. Проверить git diff, добавить только файлы пакета, исключить env. Отправить в ветку Railway. Railway запускает деплой по GitHub, если авторазвёртывание включено. Само наличие ZIP не обновляет production.

После деплоя: проверить главную с новым браузерным кэшем, догрузку нескольких рядов, смену настроения, кнопку retry, расписание, уведомления при смене аккаунта. На production искусственную задержку не включать. Проверить реальные запросы в Network: timeout теперь 20 секунд, страницы не дублируются после таймаута, общий URL расписания стабилен в пределах пятиминутного окна.

Откат: вернуть предыдущие версии файлов этой поставки и пересобрать. Миграций и новых env нет. Последующие оптимизации не считаются выполненными этим ZIP.


## Поставка 2: выполненные изменения
- Главная кэширует уже проверенный результат на 300 секунд. Проверка availability и планирование проб происходят при заполнении кэша, не при каждом чтении.
- Нездоровый registry не сохраняется как пустой успешный результат. Проверка health необходима, чтобы временная ошибка базы не скрывала главную на весь TTL.
- Публичный курсор рекомендаций остаётся общим, но номер страницы каждого выбранного источника считается отдельно. Первый seasonal/ongoing запрос начинается с первой страницы своего источника. В полном семишаговом цикле учитываются bucket, mood, intent и наличие taste genre.
- Ключ server cache строится по эффективным GetAnimesOptions. Для ranked страницы не создаются копии из-за неиспользуемого настроения/жанра/сезона.
- Новые поколения кэша: home v6, candidates v12. Старые значения не смешиваются с новой семантикой страниц и фильтрации.
- Персональное ранжирование, владение карточками рядами и ручной retry не изменены. Это улучшает доступный пул, но не гарантирует пять карточек в каждом узком персональном ряду.

Поведенческие проверки: все комбинации bucket/mood/intent/genre на 50 курсорах дают непрерывные страницы каждого источника; тёплая главная не повторяет registry read/background refresh; ошибка registry не кэшируется; реальная база с принудительным AniList outage возвращает 30 каталоговых карточек, 11 сезонных карточек и две непересекающиеся страницы рекомендаций по 20.

Эти изменения не заменяют измерение active CPU production. Wall-clock задержки и число запросов проверены отдельно; процент экономии CPU пока не установлен. ISR, межвкладочная координация и изменение частоты heartbeat плеера не внедрялись без измерений и дополнительных тестов.
