# AnimeBox: надёжность источников и восстановление Telegram после переноса

Дата: 7 октября 2026. База: main, f740f689.

## 1. Цель и границы

Пользователь находит тайтл, открывает правильное аниме и получает достоверный
результат проверки видео. Временная ошибка, неверная структура ответа или
отсутствующая настройка провайдера не должны становиться доказательством
отсутствия серии. Дополнительная цель: диагностировать и восстановить webhook
@YourAnimeBoxBot после смены хостинга через защищённую страницу админки.

Изменения поиска от 6 октября сохраняются. Ранжирование, SQL индексы,
персонализация, начисление XP и платёжная логика не требуют переработки в этой
поставке. Новые таблицы, зависимости и SQL миграции не нужны.

## 2. Подтверждённые дефекты кода

1. Kodik: `data.results ?? []` воспринимает ошибочный HTTP 200 без массива results
   как пустую выдачу. Это передаётся в реестр как отсутствие релиза.
2. Проверка AniLiberty принимает совпадение подстроки. Название сериала может
   совпасть с фильмом, продолжением или другим сезоном. Предварительное удаление
   апострофов смешивает разные релизы Gintama.
3. Плеер релиза возвращается как источник запрошенной серии, даже если самой
   серии нет в ответе. Наличие общего iframe не подтверждает отдельный эпизод.
4. Словари серий и повреждённые страницы пагинации могут превратиться в пустую
   выдачу; это создаёт ложное отсутствие эпизодов.
5. Нет MAL ID или токена Kodik: реестр считает проверку отрицательной вместо
   незавершённой. `server_busy` direct-провайдера также ошибочно считается miss.
6. При неизвестном результате Kodik теряется ранее подтверждённый max_episode.

## 3. Контракт статусов

| Условие | Статус | Действие |
| --- | --- | --- |
| Подтверждённый релиз/эпизод с допустимым источником | available | Использовать существующий путь воспроизведения |
| Валидный пустой ответ провайдера | unavailable | Использовать существующую защиту от повторных misses |
| HTTP ошибка, таймаут, повреждённый JSON/контракт | unknown | Не увеличивать счётчик подтверждённых misses |
| Не хватает ID, токена или обязательной настройки | unknown | Сохранить диагностическую причину |
| Несколько точных релизов с одинаковым названием | unknown | Не выбирать первую запись произвольно |

Существующая политика verified-first и ограниченное время сохранения ранее
проверенных карточек остаются. Патч не объявляет все непроверенные аниме доступными.

## 4. Требования к реализации источников

### Kodik

- Проверять корневой объект, массив results и элементы до фильтрации ссылок.
- Ошибочный envelope, null вместо элемента или не-HTTP(S) ссылка должны приводить
  к контролируемой ошибке; вызывающие проверки преобразуют её в unknown.
- Поддержать протокол-relative ссылки `//...` и обычные HTTP(S) ссылки.
- Пустой валидный results остаётся реальным отсутствием релиза.
- Не принимать episodes_count за количество опубликованных серий.

### AniLiberty

- Сопоставлять точное нормализованное название, сохраняя пунктуацию и подзаголовки.
- Использовать один существующий helper exactReleaseTitle для вложенных и
  верхнеуровневых полей названия.
- Исключить произвольный выбор при нескольких точных кандидатах.
- Ошибочную поисковую структуру считать unknown; валидный пустой список и 404
  обрабатывать существующим путём отсутствия релиза.
- Не подтверждать серию общим iframe, если серия отсутствует в списке.
- Поддержать массивы, пагинированные контейнеры и ordinal-keyed словари серий.
- Ошибка продолжения, повтор cursor, чужой origin или повреждённый эпизод должны
  прервать проверку, а не подтвердить неполный/пустой список.

### Реестр

- no_mal_id, provider_not_configured и server_busy — неопределённые проверки.
- Unknown не увеличивает consecutive_misses и не создаёт новый last_failure_at.
- На unknown сохранять предыдущий max_episode только для того же MAL mapping.
- Подтверждённый новый ответ имеет приоритет перед сохранёнными данными.

## 5. Telegram: факты и диагностика

Проверка 07.10.2026: анонимный POST `{}` на канонический
`https://youranimebox.com/api/telegram/webhook` вернул HTTP 401 и
`{"ok":false,"error":"unauthorized"}`. Заголовки подтвердили Cloudflare →
Railway → обработчик Next.js. По текущей логике обработчика обе обязательные
переменные заданы, иначе он возвращает server_not_configured до проверки секрета.
Это не проверка валидности токена или совпадения секретов у Telegram.

В этой сессии нет токена Telegram/доступа к управлению Railway. Причина остановки
бота пока не подтверждена. Возможные причины нужно различить по getWebhookInfo:
старый URL, неверный secret_token, доставка заблокирована, исключён message,
ошибка Bot API или ошибка обработчика. Не снимать проверку секрета для обхода.

## 6. Требования к Telegram-восстановлению

- Добавить /admin/telegram и /api/admin/telegram-webhook.
- GET допускает owner/admin, POST для восстановления — только owner через
  requireAdminMutation с существующей CSRF-защитой и ограничением запросов.
- Все вызовы Telegram выполняются сервером с TELEGRAM_BOT_TOKEN.
- Диагностика показывает наличие настроек, URL webhook, pending_update_count,
  время и безопасное описание последней ошибки, allowed_updates и совпадение URL.
- Секреты, token-containing URL и сырые исключения не отправлять клиенту.
- Перед setWebhook выполнить POST `{}` с правильным secret header на канонический
  обработчик. Запретить redirect; успех — HTTP 200 с ok:true. Этот probe не
  отправляет сообщение, не создаёт платёж и не трогает пользовательские данные.
- setWebhook использует только фиксированный канонический HTTPS URL, текущий
  TELEGRAM_WEBHOOK_SECRET и drop_pending_updates:false.
- Сохранить текущие allowed_updates и добавить message, pre_checkout_query,
  subscription: команды, Stars и состояние подписки должны доставляться.
- После восстановления повторно читать getWebhookInfo. Отдельно указать, что
  установка webhook не доказывает успешный ответ на реальную команду /start.
- Записать восстановление в существующий admin audit без секретов.

## 7. Проверки и критерии приёмки

1. Kodik `{}`, null, error envelope, повреждённый элемент/URL → unknown/ошибка,
   но `{results:[]}` → unavailable; валидные результаты продолжают работать.
2. One Piece Movie не подтверждает One Piece; Gintama' не подтверждает Gintama;
   точный релиз подтверждается; неоднозначная выдача остаётся unknown.
3. Общий iframe не подтверждает отсутствующую серию.
4. Словарь эпизодов успешно читается; повреждённые страницы не создают miss.
5. При no_mal_id/неверной настройке/server_busy реестр сохраняет unknown,
   misses/last_failure_at не меняются; прошлый max_episode не теряется.
6. Telegram диагностика не раскрывает секреты; repair сохраняет очередь,
   добавляет нужные update types, прекращается при 401/403/redirect/неуспешном
   probe и проверяет результат setWebhook.
7. Неавторизованный доступ и роль moderator не могут менять webhook.
8. TypeScript, ESLint затронутых файлов, существующие integrity/security checks,
   regression tests и production build.

## 8. Выпуск и production-проверка

В GitHub отправлять только файлы этого патча и ТЗ. Сначала reviewable ветка/PR,
без автоматического merge в main. Ветка не равна опубликованному сайту.
После выпуска на Railway owner открывает /admin/telegram, получает диагностику
и выполняет восстановление при необходимости. Затем проверяются реальный /start,
кнопки Mini App и уведомления; тестовые списания Stars не делать.
Наличие токена в новой среде само по себе не обновляет зарегистрированный webhook.

Для каталога повторить сценарий поиска → страница → серия на production с
валидными ID и на телефоне. Доступность внешних API, успешный Railway deployment
и реальная экономия CPU не объявляются подтверждёнными по одному локальному build.

- `npm run source-integrity:check`: оба набора regression tests прошли, включая
  1300 серий через 13 страниц и защиту от чужого pagination origin.
- `npx tsc --noEmit`: успешно до полной сборки; Next build также завершил TypeScript.

- Локальная сборка без production secrets использовала fallback при отсутствующем
  Supabase service role и AniList HTTP 403. Успех build не доказывает работу live DB.
- Старый `tests/routing-sources.cjs` не завершился в текущем автономном окружении:
  отсутствует внешний server-only package; при тестовой подстановке marker проверка

  доступны только серверу. Добавлен защищённый owner-путь восстановления.
